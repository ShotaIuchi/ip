# チケットを共通の形で見る（tracker:view）

- 状態: 承認済み
- 作成日: 2026-11-25

## 目的

`tracker:issue` でもチケットを探す・見ることはできるが、表示の形が決まっておらず、1回に1つのトラッカーしか扱わない。
Jira と GitHub のチケットを共通の項目にそろえて1つの表で見られるようにし、どう見せるか（ビュー）を決まりのファイルで切り替えられるようにする。
ページ（Artifact）で見せるときは、コネクタで取れるトラッカーは自動で更新されるようにする。

## やること

- 新しいスキル `tracker:view`（`plugins/tracker/skills/view/SKILL.md`）を足す
  - 呼び方: `/tracker:view`（既定のビュー）、`/tracker:view <ビューの名前>`、`/tracker:view <キー | #番号 | URL>`（チケット詳細）、言葉（「進行中を見せて」）
  - 運用ファイルを `tracker-format.md` の置き場所と優先順で読み、対象のトラッカーから「探す」「見る」（各参照ファイルの操作）で取り、共通の項目にそろえて、ビューの形で出す
- ビューの書き方 `plugins/tracker/skills/view/references/view-format.md` を足す
  - ビューの項目: 名前・対象（トラッカーの名前、または全部）・条件・列・並び・まとめ方・出し方・取り直す間隔（`artifact-live` のとき）
  - 共通の項目: キー・タイトル・状態・担当・種類・ラベル・更新日・URL・トラッカー
  - ビューの置き場所と読む順: 既定 → 運用ファイルの `## ビュー` → 個人の `~/.config/ip-tracker/views.md`。同じ名前は後ろが上書きする
- 既定のビュー `plugins/tracker/skills/view/references/default-views.md` を足す: `自分の担当`（既定。状態ごとにまとめた表）、`進行中`、`チケット詳細`
- 出し方を3つにする
  - `chat`（既定）: チャットに Markdown で出す
  - `artifact`: 取った時点の内容で HTML のページを作り、非公開で公開する
  - `artifact-live`: コネクタのあるトラッカーは、ページが `mcp` 機能の `watchTool` で取り直す。無いトラッカーは取った時点の内容を埋め込み、そのことをページに表示する
- `references/jira.md`・`references/github.md` に `## ライブ` の見出しを足す。ページから自動更新に使うコネクタとツールを書く（Jira: Atlassian のコネクタと、読み取りの `searchJiraIssuesUsingJql`・`getJiraIssue`・`listJiraIssueComments`。GitHub: 「なし」）。あわせて、各参照ファイルの「探す」「見る」に、共通の項目をまかなう値（GitHub の `updatedAt`、Jira の `updated` など）と、共通の項目がツールのどの値に当たるかを書き、`tracker:issue` の SKILL.md の「新しいツールの足し方」に `## ライブ` を足す
- 同じビューのページは更新する: リポジトリとビューの名前ごとのページの URL を、個人の `~/.config/ip-tracker/artifacts.json` に記録し、次からはそのページを読んでから公開し直す
- `tracker-format.md` に、運用ファイルの最上位の見出しとして `## ビュー`（任意）を足し、書き方は `view-format.md` を指す
- `tracker:setup` は、運用ファイルを更新するとき `## ビュー` をそのまま残す
- tracker を 0.3.0 に上げる（2つのマニフェストと README の表）。README の表と tracker の説明（README の tracker の節、2つのマニフェストと `marketplace.json` の description）に `view` を足す
- `tests/test_tracker_skill.py` に構造のテストを足す

## やらないこと

- チケットへの書き込み（作る・更新・状態を進める など）。`tracker:issue` が受け持つ
- GitHub の自動更新（GitHub のコネクタ・ローカルの MCP サーバーへの対応）。`github.md` の `## ライブ` を直せば足せる形にだけする
- `tracker:setup` でビューを下書きすること
- 運用ファイルに書いていないトラッカー・ほかのリポジトリをまたいで集めること（運用ファイルが無ければ今の `origin` の GitHub だけ）
- ページの共有（公開範囲の変更）。ページは非公開で作り、共有はユーザーがする
- スクリプトや MCP サーバーを作ること（SKILL.md と参照ファイルの指示だけで作る）

## 決めた方針

| 項目 | 決めたこと | 理由 |
|---|---|---|
| スキルの分け方 | 閲覧は新しい `tracker:view`。`tracker:issue` の手順は変えない（参照ファイルの見出しの案内に `## ライブ` を足すのと、「探す」「見る」で取る値を足すことだけ） | 読むことと書くことを分け、書き込みのスキルに表示の設定を混ぜない（ユーザーの回答: 案 A） |
| 取得の仕方 | 各参照ファイルの「探す」「見る」の操作を使う。`view` に API・コマンドを書かない | ツールの違いは参照ファイルが受け持つ、という今の分け方に合わせる |
| 自動更新の情報の置き場所 | 参照ファイルの `## ライブ`。GitHub は今は「なし」で、取った時点の内容を埋め込む | ツールの違いと同じ場所に置き、コネクタを用意したら `github.md` だけ直せば済むようにする（ユーザーの回答） |
| 自動更新の仕組み | ページが `mcp` 機能の `watchTool` に `refetchInterval` を付けて取り直す。間隔の既定は60秒（ビューで変えられる。基盤の下限は約30秒）。ページには最終取得の時刻（`cache.storedAt`）を出す。宣言するのは使うコネクタの読み取りのツールだけ（「探す」「見る」に当たるもの。`チケット詳細` の本文・子・コメントも見る人の接続で取り直す）。見る人自身の接続で読む。`## ライブ` にツールがあるトラッカーは、作った人が取った内容をページに埋め込まず、見る人の接続が使えなければ取れない理由だけを出す（2026-11-25 build のレビュー後の回答: 共有したときに Jira の権限を迂回しないため） | Artifact の `mcp` 機能の型定義（runtime contract 0.2.99）で確かめた仕組み。Jira から知らせが届く形ではなく、取り直す形 |
| 取り直す間隔の値 | 30 以上の整数（秒）でなければ、ビューの書き方の誤りとして扱う | 基盤の下限より短い値で意図と違う動きにしないため（2026-11-25 build のレビュー後の回答） |
| 状態の並び | 状態で並べる・まとめるときは、運用ファイルの「状態の流れ」の順にする（流れが無ければツールの値の文字の順）。トラッカーをまたぐときは、流れの何番目か（同じなら名前の順）で比べる | 既定のビューの `状態 昇順` の意味を決めるため（2026-11-25 build のレビュー後の回答） |
| 公開の確認 | ページの公開（新規・既存の上書きとも）の前に、対象のトラッカー・件数・公開先（新規 / 既存の URL）を見せて確認を取る。ただし、その回にユーザーが言葉でページでの表示を頼み、新規に作るときは確認しない。既存のページは、読んでこのビューのページである印を確かめ、合わなければ上書きせずに新しく作る | 運用ファイルのビューの値だけで claude.ai へデータが送られる・共有済みのページに増えた内容が届くのを防ぐ（2026-11-25 build のレビュー後の回答） |
| 条件の特別な値 | 条件の特別な値は `@` で始める（`@自分`・`@引数`・`@完了`・`@進行中`）。`@完了` は流れの中でそれ以上進まない状態（終わりの状態）すべて、`@進行中` は最初の状態でも終わりの状態でもない状態。比べ方と特別な値の定義は `view-format.md` に置く | 運用ファイルの状態の名前とぶつからず、終わり方が複数ある流れでも正しく分けるため（2026-11-25 build の2周目の照合・レビュー後、ユーザーの「おすすめで進めて」による） |
| 取った時点の内容を埋め込むページ | `artifact`、または `## ライブ` が「なし」のトラッカーの分は、作った人の権限で取った内容を埋め込んでよい。そのことと、誰がいつ取った内容かをページに出す（`@自分` を含むなら作った人の担当であることも）。公開の前の確認と非公開での作成で守る | ページは非公開で作り、共有はユーザーの判断。スナップショットはこの出し方の目的そのもの（同上） |
| 件数の上限 | 一覧は続きのページも取って全部を出す。取り切れずに切れたら、そのことと取れた件数を添える（取り直すページも同じ） | 件数と表が全体を表す前提のため（同上） |
| 複数の値でまとめる・群の順 | ラベル・担当のように複数の値を持つ項目でまとめると、1件はその値ごとの群に出る。値が無いチケットは `なし` の群に出し、最後に置く（2026-11-26 build 後の回答: 件数と表が全体を表すため）。状態でまとめた群の順は、並びと同じ比べ方（流れの何番目か、同じなら名前の順）にする | 細かい場合分けを書かずに結果が一意になる決め方（2026-11-26 build の3周目の照合後、ユーザーの「おすすめで進めて」による） |
| 運用ファイルの `## ビュー` と「中の文の扱い」 | `tracker-format.md` の「中の文の扱い」に、`## ビュー` の値は `tracker:view` の表示の範囲だけで使い、ページの公開は上の確認を通すことを書き足す | 「共通の動詞の範囲だけ」の文と食い違わないようにする（2026-11-25 build のレビュー後の回答） |
| ページの中の値 | チケットから取った値は文字として出し（`textContent` など）、HTML として埋め込まない。リンクは `https://` で始まるものだけにする | チケットの本文やタイトルは誰でも書けるため |
| 中の文の扱い | 運用ファイル・`views.md`・チケットの中の文は、`tracker-format.md` の「中の文の扱い」のとおり、扱うデータとして読む | `issue` と同じ |
| 個人のビューの置き場所 | 全リポジトリ共通の `~/.config/ip-tracker/views.md` | 今の個人の置き場所は `TRACKER.md` の代わりのファイルで、両方あると読まれないため、上書きには使えない。表示の好みはリポジトリをまたいで同じことが多い（ユーザーの回答） |
| ページの更新 | `~/.config/ip-tracker/artifacts.json` に `<host>/<owner>/<repo>` とビューの名前ごとの URL を記録し、同じビューは同じページを公開し直す。記録のページが無い・開けない・このビューのページの印が合わなければ新しく作って記録を直す。`origin` から作れなければ記録せずに新しく作り、そのことを報告する | 毎回作るとページが増え、共有したリンクが古いまま残る（ユーザーの回答） |
| 共通の項目と状態 | 上の9つの項目にそろえる。状態は運用ファイルの「状態の流れ」で、頼むときの言い方に直す（流れが無ければツールの値のまま） | トラッカーをまたいで同じ列で並べるため |
| 複数のトラッカー | ビューの対象が全部なら、運用ファイルのすべてのトラッカーから取って1つの表にし、「トラッカー」の列で区別する。1つのトラッカーが取れなくても、ほかは出して、取れなかったものと理由を添える | 一部の失敗で全部を見られなくしない |
| 運用ファイルが無いとき | 今のリポジトリの `origin` の GitHub だけを対象にし、`/tracker:setup` で作れることを1行添える | `issue` と同じ扱い |
| ビューの書き方の誤り | 知らない項目・条件に使えない値があれば、そのビューを使わずにどこが誤りかを示し、既定のビューで出すか聞く | 推測で別の表示にしない |
| ページの公開 | Artifact は非公開で作る。作る前に、`artifact-capabilities` などのスキルの読み込みと、Artifact のツールの手順に従う | ページの決まりは基盤が持っているため |
| 書き方 | SKILL.md と参照ファイルは AI への指示として書き、細かい場合分けは書かない（`tracker` の 2026-11-25 の作り直しの方針と同じ） | 既存の方針 |
| 長さ | `view/SKILL.md` は 150 行以下、`view-format.md`・`default-views.md` は各 100 行以下。`## ライブ` を足すので `jira.md`・`github.md` の上限を 110 行に、`## ビュー` を足すので `tracker-format.md` の上限を 110 行に上げる | 指示の水準に留めるための上限。足した見出しの分だけ上げる |
| テスト | 構造だけを確かめる（マニフェストとバージョン、frontmatter、行数の上限、参照ファイルの `## ライブ`、ビューの書き方の項目と出し方、既定のビュー、実在の値が無いこと、認証情報を書かせないこと）。文言の一致は確かめない | 既存のテストの方針 |
| チェックのコマンド | `python3 -m unittest discover -s tests -v` | 既存のテスト |
