# 別の AI にもレビューさせる（--with）

- 状態: 承認済み
- 作成日: 2026-11-24

## 目的

`review` と `dev:build` のレビューで、今動いている AI とは別の AI（Claude と Codex）にも同じ対象をレビューさせ、1つのレポートにまとめる。
別のモデルに見せて見落としを減らす。実装は今までどおり起動した AI（とそのサブエージェント）が行うので、書く AI と見る AI も分けられる。

## やること

- `review` スキルに `--with <AI>[,<AI>]` を足す
  - 指定した AI を、SKILL.md に書いた決まったコマンドで、対話なし・読み取りだけの権限で動かす
  - 結果は AI ごとにテキストファイルに書き出させ、すべて終わったら起動した AI が読んで統合レポートにまとめる
- `dev:build` スキルに `--with <AI>[,<AI>]` を足し、4-3 の `review` にそのまま渡す
- 前の build で入れた次のものを取り除く: `scripts/peer.py`（2か所）、`--implementer`、それに伴う SKILL.md・README・テストの記述
- テスト（`tests/`）は次だけにする
  - リポジトリの整合性: マニフェストの JSON、2つのマニフェストと README の表のバージョン
  - SKILL.md の確認: 別の AI を動かすコマンドに、決めた権限のオプションと `IP_PEER=1` が入っていること
  - これは最低限で、AC-9 やマーケットプレイスへの登録など、リポジトリの整合性を確かめるテストを足してよい
- `.gitignore` に `__pycache__/` を足し、README にテストの節を足す
- review を 0.4.0、dev を 0.3.0 に上げ、README の表と使い方を更新する

## やらないこと

- 実装・修正を別の AI に任せること（`--implementer`）。書く AI と見る AI は、レビューに別の AI を加えることで分ける
- 別の AI を動かすためのスクリプト（`peer.py` など）を置くこと。手順は SKILL.md の指示とコマンドだけで書く
- GitHub Copilot CLI を「呼ばれる側」の AI にすること（このマシンに入っておらず、確かめられないため）
- AI ごとにモデルを指定すること（各 CLI の既定のモデルを使う）
- `review-pr`、`triage`、`triage-pr`、`decompose`、`spec` に `--with` を足すこと
- `codex review`（Codex 組み込みのレビュー）を使うこと
- 呼ばれる側の読み取りを制限すること（`~/.ssh` などを読めないようにする）。README に残る危険として書く

## 決めた方針

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 指定できる AI | `claude` と `codex` | 両方の CLI で、対話なしの実行を確かめた |
| 仕組み | SKILL.md に書いた決まったコマンドを、起動した AI がシェルで実行する。スクリプトは置かない | ユーザーの回答。プロセスの管理を自前で持たず、シェルのツールに任せる |
| Codex のコマンド | `IP_PEER=1 perl -e 'alarm 900; exec @ARGV' -- codex exec --sandbox read-only --ephemeral --skip-git-repo-check --ignore-user-config --ignore-rules --disable hooks -c web_search="disabled" -C '<リポジトリ>' -o '<結果のファイル>' - < '<指示のファイル>' > /dev/null 2> '<ログのファイル>'; echo "exit=$?" >> '<ログのファイル>'` | 読み取りだけ・ネットワークなし。ユーザーやプロジェクトの設定・ルール・hooks で権限が広がらないようにする（前の build で実機で確かめたオプション） |
| Claude のコマンド | `( cd '<リポジトリ>' && IP_PEER=1 perl -e 'alarm 900; exec @ARGV' -- claude -p --permission-mode plan --setting-sources "" --strict-mcp-config --tools Bash,Read,Glob,Grep --disallowedTools WebFetch WebSearch --settings '<サンドボックスの設定>' ) < '<指示のファイル>' > '<結果のファイル>' 2> '<ログのファイル>'; echo "exit=$?" >> '<ログのファイル>'`。サンドボックスの設定は `{"sandbox":{"enabled":true,"failIfUnavailable":true,"allowUnsandboxedCommands":false,"autoAllowBashIfSandboxed":false,"network":{"strictAllowlist":true}}}` | plan だけではシェルのコマンドでネットワークに出られる（確認済み）ので、サンドボックスでネットワークを閉じる。設定ファイル・MCP・Web のツールも読まない・使わない（ユーザーの回答） |
| コマンドの書き方 | SKILL.md のコマンドは、`<…>` の部分だけを置き換えてそのまま使う、と書く。置き換えるパスは単一引用符の中に入れる。Claude は `-C` に当たるオプションが無いので、サブシェルの中の `cd` でリポジトリに移る（まとめ役の作業ディレクトリを変えず、cd の失敗もログに残る）。Codex の標準出力は捨てる（結果は `-o` のファイルに入る。呼ばれる側の出力がまとめ役に直接流れ込まないようにする） | 権限のオプションを AI が書き換えたり書き忘れたりしないようにする。空白などを含むパスで壊れないようにする。作業ディレクトリの指定を実行環境によらず1通りにする（周回1のレビューを受けたユーザーの回答） |
| 一時ファイル | `mktemp -d` でリポジトリの外に作業用のディレクトリを1つ作り、出力された絶対パスを控える。指示のファイル・AI ごとの結果とログのファイルをそこに置き、以降のコマンドにはそのパスを直接書く（シェルの変数は呼び出しをまたいで残らないため使わない）。終わったら成否に関わらず消す | 前の build のレビューで、変数が次の呼び出しで空になる問題が見つかった |
| 渡す指示 | 正確性と、今回選んだ観点を、1回の指示でまとめて頼む。レビュー対象の差分は、まとめ役がシェルで作業用のディレクトリのファイル（`diff.patch`）に書き出し（ref も単一引用符の中に入れ、除外するパスがあれば `-- . ':!<パス>'` で外す）、指示のファイルにはそのパスを書く（ファイルが対象のときはファイルの一覧） | 呼ばれる側はネットワークに出られないので、PR の差分なども先に渡す。長い差分を AI が書き写すと省略や写し間違いが起きる（周回1のレビュー） |
| 結果の形 | Markdown。重要度（Must / Should / Could / Good）ごとの見出しの下に、`[<観点>] <タイトル> — <場所>` と、理由・直し方を書く | まとめるのは AI なので、決まった JSON にしなくても読める |
| 並べ方 | 自前の観点・標準レビュー機能と同時に、別の AI のコマンドをシェルのツールでバックグラウンド実行し、すべて終わるのを待つ | 時間がかかる（数分〜十数分）ため |
| 時間の上限 | 15分。コマンドの頭の `perl -e 'alarm 900; exec @ARGV' --` で、コマンド自体が15分で終わるようにする（終了コード 142 なら「実行できず: 時間切れ」）。止まるのは perl が起動したプロセスだけで、Codex の本体（node のラッパーが起動したもの）や、呼ばれる側が起動したコマンドは、その後も自分で終わるまで動きうる。README と SKILL.md にはそう書き、「必ず終わる」とは書かない | Claude Code には15分経ったと気づくきっかけが無く、相手が固まると待ち続けてしまう。macOS には `timeout` が無い。プロセスグループごと止める仕組みは持たない（周回1・2のレビューを受けたユーザーの回答） |
| 失敗したとき | 終了コード（ログの最後の `exit=<n>` の行で見る）が 0 でない、または結果のファイルが空なら、その AI を抜いて続け、レポートに「<AI>: 実行できず（<ログの要点>）」と書く | ユーザーの回答 |
| レポートでの見せ方 | 指摘に `[<観点>/<AI>]` を付ける（例: `[正確性/codex]`）。別の AI と同じ問題なら「重複指摘」の表に載せる。`**観点**` の行に、一緒に動かした AI と結果（実施 / 実行できず: 理由 / 同じ AI のため省略）を書く | どの AI の指摘かが分かるようにする |
| 今動いている AI と同じ AI | その AI は呼ばず、レポートに「同じ AI のため省略」と書く | 同じ AI を外から呼んでも、別の見方にならない |
| `claude` と `codex` 以外の名前 | 始める前に、指定できる名前を伝えて聞く | 推測で抜くより確か |
| 呼び合いの防止 | コマンドに `IP_PEER=1` を付ける。`IP_PEER=1` のときは、スキルは `--with` を無視する | 呼ばれた側も ip のプラグインを読み込むので、呼び合いが止まらなくなるのを防ぐ |
| まとめ役がサンドボックスの中にいるとき | 別の AI のコマンドは、呼ぶたびにサンドボックスの外で動かす許可を求める（Codex がまとめ役なら常に。Claude Code はサンドボックスを有効にしているとき） | Codex のサンドボックスの中では `claude` が `Not logged in` で失敗し、外では動いた（確認済み）。ユーザーの回答 |
| チェックのコマンド | `python3 -m unittest discover -s tests -v`（標準ライブラリだけで動かす） | 依存を増やさない |

## 受け入れ条件

- AC-1: `review` の SKILL.md に、Codex と Claude それぞれの、上の「決めた方針」どおりのコマンドが書いてあり、`<…>` 以外は変えずに使う旨が書いてある（テストで、権限のオプションと `IP_PEER=1` が入っていることを確かめる）
- AC-2: `review` は `--with` を受け付け、指定した AI ごとに、自前の観点と並行してバックグラウンドで実行し、結果のファイルを読んで、指摘を `[<観点>/<AI>]` 付きで統合レポートにまとめ、`**観点**` の行に AI ごとの結果を書く
- AC-3: 今動いている AI と同じ AI を `--with` に指定すると、その AI は呼ばず、レポートに「同じ AI のため省略」と書く
- AC-4: 別の AI が失敗・時間切れ・空の結果のときは、その AI を抜いてレビューを続け、レポートに「<AI>: 実行できず（<理由>）」と書く
- AC-5: 一時ファイルは `mktemp -d` のディレクトリに置き、パスを直接書き、終わったら成否に関わらず消す、と SKILL.md に書いてある
- AC-6: `IP_PEER=1` のときは `--with` を無視する旨が、`review` と `dev:build` の SKILL.md に書いてある
- AC-7: まとめ役がサンドボックスの中にいるとき、別の AI のコマンドをサンドボックスの外で動かす許可を求める旨が、`review` の SKILL.md に書いてある
- AC-8: `dev:build` は `--with` を 4-3 の `review` にそのまま渡し、Step 5 の報告に一緒に動かした AI を書く
- AC-9: `peer.py` と `--implementer` に関するファイル・記述が、リポジトリに残っていない（仕様書と、それを確かめるテストの中の検査用の文字列は除く）
- AC-10: マニフェストの JSON が正しく、review と dev のバージョンが2つのマニフェストと README の表でそろっている（テストで確かめる）
- AC-11: README のプラグインの表と使い方に `--with` が書いてあり、呼ばれる側の権限と残る危険（読み取りは制限していない）が書いてある

## 完了の条件

- チェック: `python3 -m unittest discover -s tests -v` が成功する
- 受け入れ条件がすべて満たされている
- 本物の AI での確認（1回だけ。費用がかかるので自動のチェックには入れない）:
  1. Claude Code から、SKILL.md の Codex のコマンドを試験用のリポジトリで実行し、結果のファイルに指摘が書かれる
  2. サンドボックスの外の Codex（`codex exec --dangerously-bypass-approvals-and-sandbox`）から、SKILL.md の Claude のコマンドを実行し、結果のファイルに指摘が書かれる
  3. Claude Code で `/review:review --with codex` を試験用のリポジトリの差分に対して実行し、`[<観点>/codex]` の付いた指摘を含む統合レポートが出る
