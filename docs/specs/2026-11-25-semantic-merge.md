# 論理的なぶつかりまで見てマージする（git-kit:merge）

- 状態: 承認済み
- 作成日: 2026-11-25

## 目的

git は、同じ行を両側で変えたときしかコンフリクトを知らせない。片側が関数の引数を変え、もう片側がその関数の呼び出しを足すような
「論理的なぶつかり」は、マージは成功してもビルドやテストが壊れる。マイグレーションの番号や順番がぶつかることもある。
マージの前後でこれらを探し、マージで生まれた問題を直してからマージを確定するスキルを作る。

## やること

- `git-kit` プラグインに `merge` スキル（`plugins/git-kit/skills/merge/SKILL.md`）を足す
  - 呼び方: `/git-kit:merge [<取り込むブランチ>]`（Codex は `$git-kit:merge`）。今いるブランチに、指定したブランチを取り込む
  - 流れ: 準備 → 両側の変更を見る → 論理的なぶつかりの候補を探す → 試しにマージする → チェックを回す → 直す → 確認してマージを確定する
- git-kit を 0.2.0 に上げ、README の表と説明を更新する

## やらないこと

- `git rebase`、`git pull`、`git cherry-pick` を扱うこと
- push すること（確定した後に、push するかを案内するだけ）
- 3つ以上のブランチを一度に取り込むこと（octopus merge）
- リモートの PR を GitHub 上でマージすること
- スクリプトを置くこと
- 手順をコマンド単位で決めること（調べ方・直し方の具体的なコマンドは、そのプロジェクトに合わせて AI が決める）

## 決めた方針

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 形 | `git-kit:merge` スキル。ルールは足さない | 手順が長く、呼び出して実行する形が合う（ユーザーの回答） |
| 書き方 | SKILL.md は AI への指示として書く。目的・流れ・見るもの・守ること・止めて聞く時・報告の形を書き、git の基本操作やプロジェクトごとの調べ方・直し方はコマンドで決めない。コマンドを書くのは、流れの要になるもの（試しのマージ、中断）だけにする。長さは既存のスキルと同じくらい（250 行以下）にする | 前の版はコマンド単位の手順書（718 行）になり、レビューのたびに場合分けの穴が見つかって終わらなかった。本物の AI での確認では、ぶつかりの発見と判断は AI が自分でできた（ユーザーの回答） |
| 取り込む向き | 今いるブランチ（`ours`）に、引数のブランチ（`theirs`）を取り込む | `git merge <branch>` と同じ向きにする |
| 引数なし | 既定のブランチ（`origin/HEAD`。無ければ `main`、次に `master`）を取り込む。今いるのが既定のブランチなら、何を取り込むか聞く | 一番多い「main をブランチに取り込む」を引数なしで済ませる（ユーザーの回答） |
| リモートとのずれ | 始めに `git fetch` する。取り込むブランチ（ローカル）がリモートより古ければ、どちらの版を取り込むか聞く。今いるブランチがリモートより古い・ずれているときも伝えて聞く | 古い main を取り込むのを防ぐ（ユーザーの回答） |
| 始める前の状態 | 未コミットの変更（未追跡のファイルを含む）がある、マージ・リベースなどが途中、detached HEAD のときは、始めずに伝える。stash はしない | 自分の変更とマージの結果が混ざらないようにする |
| 早送りできるとき | 片側しか変わっていないなら、論理的なぶつかりは起きないので、そう伝えて確認してから早送りする | 調べる対象が無い |
| 論理的なぶつかりの候補 | 両側の変更（merge-base から）を見て、片側で変えた・消したものをもう片側が使っていないか、両側が同じものを新しく足していないかを探す。見るものの例: 関数・クラスの引数・戻り値・名前の変更と削除、定数・設定のキー・環境変数、API の形、マイグレーション、依存の版とロックファイル、テストの前提。探し方はプロジェクトに合わせて AI が決める | ユーザーが挙げたものとその仲間。網羅的な場合分けは書かない |
| マイグレーション | 番号・順番・依存の分岐がぶつかったら、既定のブランチの側（適用された環境がありうる）は動かさず、もう片側を付け直す（それを参照しているものも合わせる）。判断がつかないとき（どちらも既定のブランチでない、適用済みの様子がある など）は聞く | ユーザーの回答 |
| ロックファイル | 文字の上でマージした結果を信じない。両側が依存を変えたときは、マージした宣言からパッケージマネージャーで作り直し、片側が上げた版が消えていないか確かめる | ロックファイルの行のマージは正しくならない（ユーザーの回答） |
| 試しにマージ | `git merge --no-commit --no-ff` で取り込み、確定はしない。文字のコンフリクトは、両側の意図を読んで解く | 確定する前に、結果を確かめて直せるようにする |
| チェック | プロジェクトのチェック（ビルド・型・テスト・lint・マイグレーションの確認）を探し、マージした結果で実行する。失敗したら、両側の版でも同じかを確かめ、元からの失敗と、マージで生まれた問題を分ける | 論理的なぶつかりは、実際に動かすと分かることが多い |
| コマンドの実行の確認 | チェックなど、プロジェクトのコマンド（依存の準備・ロックファイルの作り直しを含む）を実行する前に、毎回、実行するコマンドを示して確認を取る | 取り込む側のコード（scripts・postinstall・Makefile など）が手元で動くため（ユーザーの回答） |
| 見つけたときの扱い | 直し方が1つに決まるものは直して報告する。どちらの意図に寄せるかの判断が要るもの（新しい引数に渡す値、両側が同じものを別の形に変えた、仕様が食い違う など）は、止めて選択肢とおすすめを示して聞く | ユーザーの回答 |
| 直した変更の置き場所 | マージコミットに含め、メッセージに、見つけた論理的なぶつかりと直した内容を書く | どのコミットでもビルドとテストが通る状態を保つ（ユーザーの回答） |
| 確定 | 報告を示し、確認してから `git commit` でマージを確定する。`--no-verify` は使わない | ユーザーの回答 |
| やめるとき | 中断なら `git merge --abort` でマージの前に戻す（このスキルが始めたマージだけ）。その後に残った未追跡のファイルは、このスキルが作ったものだけ消し、それ以外は一覧にして聞く。`git clean` は使わない | 始める前の状態に戻す。ユーザーが途中で作ったファイルを消さない（ユーザーの回答） |
| 報告 | 取り込んだ向き、文字のコンフリクトとその解き方、論理的なぶつかりの候補と結果（問題なし / 直した / 聞いた）、チェックの結果、マージコミット | 何を確かめて何を直したかが分かるようにする |
| 実行環境 | Claude Code・Codex・Copilot CLI で同じ指示にする | 既存のスキルと同じ |
| チェックのコマンド（このリポジトリ） | `python3 -m unittest discover -s tests -v` | 既存のテスト |

## 受け入れ条件

- AC-1: `plugins/git-kit/skills/merge/SKILL.md` があり、frontmatter に `name: merge` と、起動の言い方（「マージして」「main を取り込んで」など）を含む `description` と、`argument-hint` がある
- AC-2: SKILL.md に、引数なしのときの取り込むブランチ、`git fetch` とリモートとのずれの扱い、始める前の状態の確認が書いてある
- AC-3: SKILL.md に、両側の変更から論理的なぶつかりの候補を探すことと、見るものの例（引数・名前・削除、両側で同じものを足す、定数・設定・環境変数、API の形、マイグレーション、依存とロックファイル、テストの前提）が書いてある
- AC-4: SKILL.md に、`git merge --no-commit --no-ff` で試しにマージし、チェックを実行する前に確認を取り、失敗を両側と比べてマージで生まれた問題を分けることが書いてある
- AC-5: SKILL.md に、直し方が1つに決まるものは直し、判断が要るものは止めて聞くこと、直した変更をマージコミットに含めてメッセージに書くこと、確認してから確定すること、中断なら `git merge --abort` して自分が作ったファイルだけを消すことが書いてある
- AC-6: SKILL.md に、早送りできるときの扱いと、push しないことが書いてある
- AC-7: SKILL.md が 250 行以下である。git-kit のバージョンが 0.2.0 で、2つのマニフェストと README の表でそろっている。README の表と説明に `merge` が書いてある

## 完了の条件

- チェック: `python3 -m unittest discover -s tests -v` が成功する
- 受け入れ条件がすべて満たされている
- 本物の AI での確認（1回だけ）: 試験用のリポジトリで、片側が関数の引数を変え、もう片側がその関数の呼び出しを足し、両側が同じ番号のマイグレーションを足したブランチを作る。作業ツリーのプラグインを読み込んだ Claude Code で `/git-kit:merge` を実行し、git のコンフリクトが無いのに両方の論理的なぶつかりを見つけて報告し（直し方が1つに決まるものは直し、判断が要るものは聞く）、確認の前に確定しないことを確かめる
