# レビューと修正を、指摘が無くなるまで繰り返す（review:loop）

- 状態: 承認済み
- 作成日: 2026-11-25

## 目的

今の変更を「レビュー → 直す」を手で繰り返すには、`review:review` と `review:triage` を交互に呼ぶしかない。
`dev:build` は繰り返すが、承認済みの仕様書が要る。仕様書なしで、今の変更をレビューして直すことを、指摘が無くなるまで（最大 N 周）自動で回すスキルを作る。

## やること

- `review` プラグインに `loop` スキル（`plugins/review/skills/loop/SKILL.md`）を足す
  - 呼び方: `/review:loop [<対象>] [--max-rounds <N>] [--with <AI>[,<AI>]]`（Codex は `$review:loop`）
  - 流れ: 準備 → [ チェック → レビュー（`review:review`）→ 直すものを決める → 直す ] × 最大 N 周 → 報告
- review を 0.5.0 に上げ、README の表と説明を更新する

## やらないこと

- コミット・push すること（最後に `git-kit:commit` を案内する）
- PR のコメントに対応すること（`triage-pr` の役目）。PR を対象にすること
- 仕様との照合（仕様書があるなら `dev:build` を使う）
- スクリプトを置くこと。手順をコマンド単位で決めること（`git-kit:merge` と同じく、AI への指示の水準で書く）
- `review`・`triage`・`dev:build` の振る舞いを変えること

## 決めた方針

ユーザーが寝ている間に作るため、聞かずに、会話で示したおすすめ（新しいスキル `review:loop`、`dev:build` の手順4を仕様の照合なしで切り出す）と、`dev:build` の決まりに合わせて決めた。

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 形 | `review` プラグインの新しいスキル `loop`。`triage` に `--loop` を足すのではなく分ける | `triage` は「調べて、ユーザーが選んだものを直す」対話のスキルで、自動で回す `loop` とは進め方が違う。会話で示した第一案 |
| 書き方 | AI への指示の水準（目的・流れ・決まり・止めて聞く時・報告の形）。250 行以下 | `git-kit:merge` で、コマンド単位の手順書は穴が尽きないと分かったため（ユーザーの回答） |
| 対象 | 今の変更（作業ツリーの未コミットの変更。無ければ、既定のブランチとの分岐点から HEAD まで）。`since <ref>`、`branch BASE..HEAD`、ファイルパスも受け付ける。ファイルパスは、そのファイルの未コミットの変更だけを対象にする（変更が無いファイルは受け付けない）。PR は受け付けない | 直すので、手元にある変更が対象になる。ファイル全体を直すと、変更していない部分まで広がるため（レビューの指摘を受け、まとめ役が狭い方を選んだ） |
| 起点 | 始めたときの対象の起点（コミット）を控え、毎周、その起点から作業ツリーまでをレビューする（直した変更も含めて見る）。新しく作ったファイルも差分に入るようにする | `dev:build` と同じ。直したことで生まれた問題も次の周で見る |
| 始める前の状態 | マージ・リベースなどの途中なら始めない。未コミットの変更はそのまま対象にする（退避・破棄しない） | 今の変更を直すスキルなので、未コミットの変更が対象そのもの |
| 周回 | 既定 3 周。`--max-rounds <N>` で変えられる。上限は修正の回数で、上限の周の修正の後にもう一度だけチェックとレビューをして結果を確かめる | `dev:build` と同じ |
| チェック | プロジェクトのチェック（テスト・ビルド・lint・型）を探して毎周実行する。失敗も直す対象にする。見つからなければ一度だけ聞く | 直したことで壊していないかを確かめる |
| レビュー | `review:review` を `since <起点>` で呼ぶ。`--with` は始める前に名前を一度だけ確かめ（`dev:build` と同じ）、その一覧を毎周渡す。`review` が無い環境では、標準レビュー機能を直接呼ぶ | 既存のスキルを使う |
| 直す対象 | チェックの失敗、Must と Should。Could は直さずに記録する。前の周で誤りと判断して直さなかった指摘が同じ場所・同じ内容でまた出たら直さない | `dev:build` と同じ |
| 直し方 | 修正係（サブエージェント。起動できない環境では自分）に任せる。直す前に原因を調べ、症状ではなく原因を直す。指摘が誤っていると判断したら直さずに理由を返す。テストを曲げない | `dev:build`・`triage` と同じ |
| 止めて聞く時 | 直すために、公開 API・保存するデータの形・既存の振る舞いを変える、依存を足す、頼まれた範囲を超えて広げる、設計を変える必要がある。直し方が行き来する（前の周で直した箇所に同じ指摘・逆向きの指摘が出た） | 仕様書が無いので、範囲と方針の判断はユーザーに聞く |
| 終わり | 直す対象が 0 件になったら完了。上限に達したら、残った問題を報告して止まる | |
| 報告 | 周回・状態（完了 / 上限で停止 / 行き来で停止 / 質問待ち）、直したもの（周・出どころ）、直さなかったもの（理由）、チェックの結果、変更の stat。最後に `git-kit:commit` を案内する | `dev:build` の報告に合わせる |
| コミット | しない | 直した結果を確かめてからコミットしてもらう |
| チェックのコマンド（このリポジトリ） | `python3 -m unittest discover -s tests -v` | 既存のテスト |

## 受け入れ条件

- AC-1: `plugins/review/skills/loop/SKILL.md` があり、frontmatter に `name: loop`、起動の言い方（「レビューして直して」「指摘が無くなるまで」など）を含む `description`、`argument-hint` がある
- AC-2: SKILL.md に、対象と起点の決め方、周回の上限（既定 3、`--max-rounds`）、チェック → `review:review`（`--with` を渡す）→ 直すものを決める → 修正係 の流れが書いてある
- AC-3: SKILL.md に、直す対象（チェックの失敗・Must・Should。Could は記録）と、前の周で退けた指摘を直さないこと、止めて聞く時、行き来したら止めることが書いてある
- AC-4: SKILL.md に、コミット・push しないこと、テストを曲げないこと、報告の形（最後に `git-kit:commit` を案内）が書いてある
- AC-5: SKILL.md が 250 行以下である
- AC-6: review のバージョンが 0.5.0 で、2つのマニフェストと README の表でそろっている。README の表に `loop` が書いてある
