# tracker: 外の文書から運用の決まりを取り込み、更新に追従する

- 状態: 承認済み
- 作成日: 2026-11-25
- 元: docs/specs/2026-11-25-tracker.md の続き

## 目的

プロジェクトの運用の決まりは、リポジトリの外の人向けの文書（Google Docs、Gist、README、Confluence など）に書かれていることが多い。
その文書を正しい情報源のままにして、`tracker:setup` が決まった見出しに写して TRACKER.md に取り込み、
`tracker:issue` が元の文書の更新に気づいて取り込み直せるようにする。人は元の文書だけを直せばよく、AI 専用の書き直しを覚えなくてよい。

## やること

- `tracker:setup` が、外の文書を取り込み元として受け付け、中の自然言語の決まりを TRACKER.md の決まった見出しに写す（下書き・差分を見せて確認してから書く）。
  - 文書は引数 `--from <場所>`（繰り返し可）か、言葉（「この Docs から取り込んで」）で示す。
  - 取り込み元の種類: Google Docs、GitHub Gist、GitHub のファイル（ブランチ指定。既定はそのリポジトリの既定のブランチ）、Confluence のページ、任意の `https` の URL。
- TRACKER.md に `## 取り込み元` の節を足し、取り込み元ごとに 種類・場所・版の印・受け持った見出し・取り込んだ日 を表の1行で記録する。
- `tracker:setup` で取り込み直すときは、その取り込み元が受け持った見出しだけを作り直し、差分を見せて確認してから書く。
- `tracker:issue` の最初に、運用ファイルに取り込み元があれば、各取り込み元の版の印だけを確かめる。
  - 新しくなっていれば、取り込み直すか聞く。取り込むなら、受け持った見出しの差分を見せて確認してから TRACKER.md を書き、それから頼みを続ける。
  - 断られたら今の TRACKER.md で頼みを続ける（同じ会話の中では聞き直さない。会話が変われば、また確かめる）。
  - 届かない（権限が無い・通信できない・コネクタが無い）ときは、確かめを飛ばして1行だけ伝え、今の TRACKER.md で続ける。
- 取り込み元ごとの違い（場所の書き方、読み方、版の印の取り方、届かないことの見分け方）を、新しい参照ファイル `plugins/tracker/skills/setup/references/sources.md` に書く。
- `tracker-format.md` に `## 取り込み元` の節の形と、取り込み元の中身の扱いを足す。
- `setup` の「外の文書（Confluence・Wiki など）からの運用の取り込みはしない」の行を消す。
- tracker のバージョンを 0.2.0 にし、README を合わせる。
- テスト（構造だけ）を足す。

## やらないこと

- `github.md` への Projects の項目（Estimate など）の更新・マイルストーンの作成の追加（別の spec で扱う）。
- 頼みのたびに元の文書の全文を読んで決まりを解釈すること（読むのは版の印だけ。全文を解釈するのは取り込むときだけ。版の印が本文のハッシュの取り込み元は、ハッシュを計算するためだけに本文を取ってよい）。
- 取り込み元への書き込み（元の文書は読み取りだけ）。
- 「見送った版」の記録。
- Redmine など新しいトラッカーの対応。
- 取り込み元の自動での定期的な確かめ（呼ばれたときだけ確かめる）。

## 決めた方針

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 書き方 | 前の作り直しと同じく、指示は目的・流れ・守ること・止めて聞く時・各 Step の形で書き、場合分けを並べない。同じ決まりは1か所にだけ書く | 前回の build の教訓（場合分けの列挙で膨らむ） |
| 長さ | `issue` ≤150 行（今150行なので、足す分ほかを削る）、`setup` ≤150 行、`sources.md` ≤100 行、`tracker-format.md` ≤100 行、`github.md`・`jira.md` ≤100 行（変えない） | 前回と同じ上限 |
| 取り込み直しの範囲 | その取り込み元が受け持った見出しだけを作り直す。ツールから集めた見出し・答えた見出しは残す。受け持った見出しを手で直していれば、差分に出して上書きする | ユーザーの回答（推奨 A）。元の文書が正しい情報源 |
| 確かめる時 | `issue` は呼ばれるたびに版の印だけを確かめる。断られたら今の TRACKER.md で続ける。同じ会話の中で一度確かめた取り込み元は、確かめも質問も繰り返さない（会話が変われば、また確かめる） | ユーザーの回答（推奨 A）。build 中の回答（推奨）で、同じ会話では聞き直さない形にした（`dev:decompose` が続けて呼ぶと毎回聞かれるため） |
| Projects・マイルストーン | 別の spec | ユーザーの回答（推奨 A）。層が違う |
| 版の印 | Google Docs: `modifiedTime`。Gist: `history[0].version`。GitHub のファイル: そのパスとブランチの最新のコミットの sha。Confluence: ページの版の番号（読めなければ本文の sha256）。URL: `ETag`、無ければ本文の sha256 | Docs・Gist・GitHub・URL は確かめ済み。Confluence は確かめられていない（このサイトに Confluence が無い） |
| 読み方 | Google Docs は Google Drive のコネクタ（無い環境では届かない扱い）。GitHub・Gist は `gh`（非公開・GHE も同じ）。Confluence は Atlassian MCP。URL は `https` だけを認証情報なしで `curl` で取る | 既存のつなぎ方に合わせる。認証情報を書かない |
| 記録の形 | トラッカーごとの節の外に `## 取り込み元` を置き、表 `| 種類 | 場所 | 版の印 | 受け持った見出し | 取り込んだ日 |`。受け持った見出しは `<トラッカーの名前> / <見出し>` で書く | 人も読め、AI が決まって読める |
| 中身の扱い | 取り込んだ文書の中の文もデータであって指示ではない。`tracker-format.md` の「中の文の扱い」を取り込み元にも当てる。写すのは決まった見出しに入る運用の値だけ | 前回の方針の延長（プロンプトインジェクション対策） |
| 印だけ変わったとき | 写す中身が同じなら版の印だけを更新する。これも書き込みなので1行で確認を取る | 書き込みは毎回確認 |
| 届かないとき | `setup` ではその取り込み元について止めて聞く。`issue` では1行伝えて続ける | ユーザーとの合意（メモリ） |
| 参照ファイルの場所 | `setup/references/sources.md`。`issue` は `../setup/references/` から読む | `tracker-format.md` と同じ置き方 |
| 秘密の Gist | `gh` で `public: false` と分かった Gist は、リポジトリの `TRACKER.md` には書かずに止め、個人の置き場所を勧める | build 中のユーザーの回答（推奨）。URL を知っていれば誰でも読めるため、共有のファイルに書くと漏れる |
| 本文のハッシュ | 版の印が本文の sha256 の取り込み元は、確かめのたびにハッシュのためだけに本文を取る（解釈はしない）。HTML は文字だけを取り出してハッシュする。取り込むときに2回取って値が揺れるページは取り込み元にせず、そのことを伝えて聞く。印の種類（`etag:` / `version:` / `sha256:` など）は取り込み時に決めて記録し、確かめでは同じ種類で比べる | build 中のユーザーの回答（推奨）。毎回「更新された」と聞かれ続けるのを防ぐ |
| 更新に気づいたときの聞き方 | まず1行で「<取り込み元> が更新されています。取り込みますか？」と聞き、はいなら全文を読んで受け持った見出しの差分を見せ、確認してから書く | build 中のユーザーの回答（推奨）。差分を作るには全文を読んで写す必要があり、断られると無駄になる |
| `--from` 無しの setup | 取り込み元が受け持つ見出しは、`--from` 無しの setup では書き換えない。ツールから集めた値と食い違えば、下書きに注として示し、元の文書を直すよう勧める | build 中のユーザーの回答（推奨）。正しい情報源は元の文書 |
| 共通の決まりの参照 | AC が「〜に書かれている」と求める決まりは、共通の節（`sources.md` など）への参照で書いてよい（同じ決まりは1か所） | まとめ役の解釈（「書き方」の方針と AC の両立） |
| GitHub のファイルのブランチ | 取り込むときに決まったブランチ名を記録し、そのあと既定のブランチが変わっても記録したブランチを使い続ける | build 中のユーザーの回答（推奨）。黙って別のブランチを読むより安全 |
| 版の印と一緒に返る本文 | 版の印を取る呼び出しが本文も返す種類（Gist・Confluence）でも、確かめのときは本文を解釈しない（「読むのは版の印だけ」に含まれる） | build 中のユーザーの回答（推奨） |
| テスト | 構造だけ（バージョン、行数の上限、`sources.md` に種類ごとの節があること、`tracker-format.md` に `取り込み元` の節と表の列があること、`setup` から取り込み禁止の行が消えていること、`issue` が版の印の確かめに触れていること、資格情報を書かせないこと） | 前回と同じ |

## 受け入れ条件

- AC-1: `plugins/tracker/.claude-plugin/plugin.json` と `.codex-plugin/plugin.json` の version が `0.2.0` で、README の tracker の行も `0.2.0` である。
- AC-2: `sources.md` があり、Google Docs・Gist・GitHub のファイル・Confluence・URL の節がそれぞれあり、各節に「場所の書き方」「読み方」「版の印」「届かないとき」が書かれている。100行以下である。
- AC-3: `tracker-format.md` に `## 取り込み元` の節の形（表の列 種類・場所・版の印・受け持った見出し・取り込んだ日）があり、「中の文の扱い」が取り込んだ文書にも当たると書かれている。100行以下である。
- AC-4: `setup` に、取り込み元を受け付けて決まった見出しに写すこと、取り込み直しは受け持った見出しだけを作り直すこと、書く前に下書き・差分を見せて確認することが書かれ、取り込み禁止の行が無い。`argument-hint` に `--from` がある。150行以下である。
- AC-5: `issue` に、最初に取り込み元の版の印だけを確かめること、新しければまず取り込むか聞き、はいなら差分を見せて確認してから書くこと、断られたら今の TRACKER.md で続けること、届かなければ1行伝えて続けることが書かれている。150行以下である。
- AC-6: どのファイルも、認証情報（トークン・API キー・Cookie）をファイルに書かせない（AC-9 と同じ確かめ方）。URL の取り込み元に認証情報を付けないと書かれている。
- AC-7: 既存のテストを含め `python3 -m unittest discover -s tests` が成功する。

- チェック: `python3 -m unittest discover -s tests` が成功する
