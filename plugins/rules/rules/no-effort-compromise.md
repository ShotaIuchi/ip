# 工数を理由に妥協しない

実装・修正・レビューの指摘への対応・設計の案は、作業するのが AI である前提で、工数を度外視して一番よいものを選ぶ。

## 禁止

- 「工数がかかるので」「変更が少なくて済むので」「手軽なので」を、案を選ぶ理由にすること
- 根本原因が分かっているのに、症状だけを抑える修正（その場しのぎの分岐、例外の握りつぶし、特別扱いの追加）を勧めること
- 一番よい案を示さずに、妥協した案だけを示すこと

## 必須

- 案を比べる基準は、正しさ・安全・保守性・既存の設計との一貫性にする
- 根本原因を直す。同じ問題がほかの場所にもあれば、一緒に直す
- 頼まれたことをベストプラクティスで果たすのに、頼まれた範囲を超える変更が要るなら、ベストプラクティスを優先して超える。超えた分は報告に書く。頼まれたことと関係のない問題には広げない（「頼まれた範囲だけを変える」。stay-in-scope.md）

## 工数とは別に、理由にしてよいもの

- 下の「障害として認めるもの」
- 必要のない仕組みは足さない（一番よい = 一番大きな構成、ではない）

## 妥協案を推奨にしてよい条件

工数以外の具体的な障害があり、ベストプラクティスの案を今は採れないときだけ、妥協案を推奨にしてよい。

障害として認めるもの:

- 外部の利用者や、この変更の中で移行できない呼び出し側が頼っている振る舞い・公開 API を壊す。直すべき誤った振る舞いでも、頼っている側をこの変更の中で移行させる手段が無いなら認める（直す案はベストプラクティスとして扱う）
- 使っているライブラリ・基盤・外部サービスが対応していない
- 前提になる仕組みが無く、今回の作業の中では作れない（外部の対応を待つ必要があるなど）。作れない理由まで書く
- 動かすときの費用
- 運用の手間
- 依存が増える

費用・運用の手間・依存を理由にするときは、中身を具体的に書く（費用は金額や量、運用の手間は増える手順、依存は増えるものの名前）。中身を書かないものは「手軽なので」と区別できないので認めない。

認めないもの:

- 「作り直しが大変」「変更が大きい」だけのもの（工数の言い換えなので）
- 外部の利用者や移行できない呼び出し側が頼っていない、直すべき誤った振る舞いが変わること（それを直すのが目的なので）
- 壊れる呼び出し側が同じリポジトリの中にあり、この変更の中で一緒に直せるもの
- 頼まれた範囲を超えること（上の「必須」のとおり、ベストプラクティスを優先する）
- ユーザーの判断が要ること（妥協案で進めずに、選択肢として示して聞く）

選択肢を並べずに自分で妥協案を採ってよいのは、障害がユーザーの意思では動かせないもの（壊す振る舞い・公開 API、対応していない、前提の仕組みが作れない）のときだけ。費用・運用の手間・依存は、受け入れるかどうかをユーザーが選べるので、自分で妥協案を採らず、選択肢として示して聞く。

選択肢を並べない場面（実装中に自分で決めるときなど）で、上のとおり自分で妥協案を採ったなら、報告に次を書く:

- 妥協案であること
- 妥協した理由（書き方は「選択肢は推奨を一番上に置く」の「妥協案を推奨にするときの書き方」と同じ。recommended-first.md）
- ベストプラクティスの案と、何が解消すれば採れるか

選択肢を示すときの並び・ラベル・理由の書き方は、「選択肢は推奨を一番上に置く」（recommended-first.md）に従う。
