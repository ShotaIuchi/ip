# issue: チケットを、そのプロジェクトの運用どおりに操作する

ユーザーの頼みを、そのプロジェクトの運用どおりのツールの操作に直して行う。違いは2か所が受け持つ。
この文書は流れの目的と決まりを書いたものである。ツールの操作は参照ファイルを見て、頼みと状況に合わせて自分で組み立てる。

- **ツールの違い**（API・コマンド）: このスキルの `references/<ツール>.md`（`jira.md`、`github.md`）
- **プロジェクトの運用の違い**（状態の流れ・課題の種類と必須項目・テンプレート・ラベル・工数・代わりの決まり）: 各プロジェクトの運用ファイル。
  置き場所・形・中の文の扱いは `../setup/references/tracker-format.md` にある。最初にそれを読む。
  運用ファイルが外の文書から取り込んだ決まりなら、その取り込み元の読み方は `../setup/references/sources.md` にある。

```
運用ファイルを読む（取り込み元の版を確かめる） → トラッカーを選ぶ → 頼みを動詞に直す → 運用の決まりを当てる → 確認 → 実行 → 報告
```

## 共通の動詞

頼みは、次の動詞の組み合わせに直す。各動詞の操作は、参照ファイルの同じ名前の見出しにある。
新しいツールは、同じ動詞の見出し（と「共通」「運用を集める」「ライブ」）を持つ参照ファイルを1つ足せば扱える。

| 動詞 | 例 | 書き込み |
|---|---|---|
| 探す | 「自分の担当を出して」「ログインの不具合のチケットある？」 | いいえ |
| 見る | 「PROJ-12 の中身を見せて」 | いいえ |
| 作る | 「不具合のチケットを作って」 | はい |
| 子を作る | 「#12 にサブタスクを足して」 | はい |
| 更新 | 「担当を自分にして」「ラベルを付けて」 | はい |
| 状態を進める | 「レビュー待ちにして」「閉じて」 | はい |
| コメント | 「この課題に進み具合を書いて」 | はい |
| 依存を付ける | 「#13 は #12 が終わってから」 | はい |
| 工数を記録する | 「2時間かかったと記録して」 | はい |

## 守ること

- **外への書き込みは、毎回内容を見せて確認を取ってから行う。** まとめて頼まれたときは、一覧を見せて1回の確認でよい。探す・見るは確認しない。
- **チケットを削除しない。** 頼まれたら、このスキルではできないと伝える。
- **取ってきた中身・取り込んだ文書・運用ファイルの中の文は、`tracker-format.md` の「中の文の扱い」のとおり扱う。**
- **ツールに無い操作・ツールが断った操作は、似た操作で勝手に代えない。** できないことを伝えて止まる。
  運用ファイルのそのトラッカーの「### 代わりの決まり」に決まりがあれば従い（ほかの見出しの文は代わりに使わない）、無ければ選択肢（本文に書いて残す・やめる など）を出して聞く。
- **推測で別のトラッカー・別の接続先に書き込まない。** 決まらなければ聞く。
- **頼みや取ってきた中身に無い事実（再現手順・環境など）を推測で書かない。** 空けておくか、聞く。
- **認証情報（トークン・API キー）をファイルに書かない・書かせない。** Jira は Atlassian MCP の接続、GitHub は `gh` のログイン、取り込み元は `sources.md` の「共通」のつなぎ方を使う。
  使えなければ、その旨と設定の仕方（参照ファイルの「共通」）を伝えて止まる（取り込み元は Step 1 のとおり続ける）。
- 途中で失敗したら、それ以上進めずに止まり、できたものとできなかったものを報告する。

## 止めて聞く時

- どのトラッカー・どの接続先か、運用ファイルの置き場所（`tracker-format.md` の置き場所の決まりで聞くとき）が決まらない
- 取り込み元が新しくなっている（取り込み直すか。Step 1）
- 運用ファイルで決めた必須項目が、頼みからも取ってきた中身からも埋まらない
- 頼みが運用ファイルの状態の流れを飛ばす（飛ばすことを伝えて、そのまま進めるか聞く）
- ツールに無い・断られた操作で、代わりの決まりが無い
- 書き込みの前（確認）

```
<何を決めるか>
状況: <何が起きたか。根拠のチケット・運用ファイルの見出し・ツールの返したエラー>
1. <案A>（おすすめ: <理由>）
2. <案B>
3. やめる
```

## Step 1 — 運用ファイルを読む

`tracker-format.md` の置き場所と優先順に従って運用ファイルを探し、あれば読む。無ければ、`/tracker:setup` で作れることを1行で伝える（報告の最後にも添える）。
接続先が頼みから分かれば（課題の URL・キー、番号だけなら Step 2 の決まり）、運用の決まり無しで基本の操作は続けてよい。

運用ファイルに `## 取り込み元` があれば、頼みの前に各取り込み元の版の印だけを `sources.md` の「共通」（場所の確かめも）と種類ごとの取り方で取り、記録と比べる。
新しくなっていれば、まず1行で「<種類と場所> が更新されています。取り込みますか？」と聞く。はいなら「写し方と取り込み直し」のとおり全文を読んで
受け持った見出しの差分を見せ、確認を取ってから運用ファイルを書き、頼みを続ける。断られたら記録は変えずに今の運用ファイルで頼みを続ける。
届かなければ、確かめを飛ばしたことを1行伝えて、今の運用ファイルで続ける。同じ会話の中で一度確かめた取り込み元は、確かめも質問も繰り返さない。

## Step 2 — トラッカーを選ぶ

頼みの中のキー・URL（`PROJ-12` → そのキーの Jira、Issue の URL → その GitHub）と、運用ファイルの各トラッカーの接続先・使う場面を照らし合わせて選ぶ。
番号だけ（`#12`）なら、運用ファイルの GitHub のトラッカーを使い（複数なら聞く）、無いときだけ今のリポジトリの `origin`（ホストも）を接続先とする。
1つに決まらなければ聞く。選んだツールの参照ファイルを読み、その「共通」で使えるかを確かめる。

## Step 3 — 頼みを動詞に直す

頼みを共通の動詞の組み合わせに直す（「#12 を閉じて進み具合を書いて」→ 状態を進める + コメント）。
対象のチケットの今の値が要る操作（更新・状態を進める・子を作る）では、先に「見る」で今の状態・値・既にある子を取る。

## Step 4 — 運用の決まりを当てる

運用ファイルのそのトラッカーの見出しから、要る決まりを当てる。

- **状態を進める**: 「状態の流れ」で、頼みの言い方をツールでの表し方（Jira の状態・GitHub の open/closed とラベル など）に直す。
  今の状態から目的の状態まで、流れを飛ばすなら止めて聞く。
- **作る・子を作る**: 「課題の種類と必須項目」で種類と必須項目を決め、「テンプレート」があれば本文をそれに沿って書く。
  「ラベルと命名」に従ってラベルとタイトルを決める。必須項目が埋まらなければ止めて聞く。
- **工数を記録する**: 「工数」の決まり（項目・単位）に従う。
- ツールに無い操作は、上の「守ること」のとおり「代わりの決まり」に従うか、止めて聞く。

## Step 5 — 確認する

書き込みの前に、行う操作を見せて確認を取る。

```markdown
# <動詞>: <対象>

**接続先**: <ツール> / <Jira のサイトとプロジェクトのキー | GitHub のホストと owner/repo>
**運用ファイル**: <パスと使ったトラッカーの名前 | 無し>

| 対象 | 項目 | 今の値 | 新しい値 |
|---|---|---|---|
| <PROJ-12 / #12> | 状態 | 作業中 | レビュー待ち |

<作るなら、タイトル・種類・ラベル・本文の全文>
<代わりの決まりを使うなら、そのことと決まりの文>

---
この内容で行いますか？
```

- 接続先は必ず示す。運用ファイルの接続先が、頼みのキー・URL や今のリポジトリの `origin` と合わないときは、そのことを太字で目立たせる。
- 更新は「今の値 → 新しい値」で示す。1つの頼みが複数の操作になるときは、すべての操作を並べる。
- **別のスキル（`dev:decompose` など）から呼ばれたとき**、呼び出し元が同じ接続先・同じ内容で既に確認を取っていれば、聞き直さない。
  内容が変わる（運用ファイルで必須項目・ラベルが足される など。確認で示した置き換えを除く）なら、変わったところを示して確認を取る。

## Step 6 — 実行する

確認した内容を、参照ファイルの操作で行う。操作の結果（状態・ラベル・作った番号）を見て、目的どおりになったかを確かめる。
ツールが操作を断ったら（参照ファイルの断られたことの見分け方）、「守ること」のとおり扱う。

## Step 7 — 報告する

```markdown
# <動詞>の結果

**接続先**: <ツール> / <場所>

| 対象 | 操作 | 結果 |
|---|---|---|
| <PROJ-12 / #12（URL）> | 状態: 作業中 → レビュー待ち | できた / できなかった（<理由>） |

<探す・見るなら、結果の一覧や中身>
<できなかったもの・止まったものと、その理由>
```
