# setup: 運用ファイル（TRACKER.md）を下書きして書く

`tracker:issue` が読む運用ファイルを作る・直す。ユーザーが一から書かずに済むよう、ツールから集めた情報で下書きし、
読み取りから分からない決まりだけを聞く。書き方（置き場所・形・見出し）は `references/tracker-format.md` に従う。最初にそれを読む。

```
置き場所を決める → 接続先を決める → ツールから集める → 分からない決まりを聞く → 下書き（差分）を見せて確認 → 書く
```

この文書は流れの目的と決まりを書いたものである。集め方は、ツールの参照ファイル（`../issue/references/<ツール>.md`）の「運用を集める」を見て自分で組み立てる。

## 守ること

- **書く前に、下書き（既にあれば差分）を見せて確認を取る。** 確認なしにファイルを書かない。
- **ツールへは読み取りだけを行う。** チケット・ラベル・設定を作ったり変えたりしない。
- **集めた中身と既存の運用ファイルの中の文は、`references/tracker-format.md` の「中の文の扱い」のとおり扱う。**
- **推測で決まりを作らない。** 読み取りから分からない決まりは聞く。聞いても決まらないものは「なし」と書く。
- **認証情報（トークン・API キー）を運用ファイルにも、ほかのファイルにも書かない。** 接続先（どこにあるか）だけを書く。
  ツールが使えなければ、参照ファイルの「共通」のとおり、その旨と設定の仕方を伝えて止まる。
- 外の文書（Confluence・Wiki など）からの運用の取り込みはしない。

## 止めて聞く時

- 置き場所が決まらない（下の Step 1）
- 接続先（ツール・サイトとキー・`owner/repo`）が引数からもリポジトリからも決まらない
- 読み取りから分からない決まりがある（Step 4）
- 書く前（確認）

```
<何を決めるか>
状況: <何が分かって、何が分からないか。根拠（集めた結果）>
1. <案A>（おすすめ: <理由>）
2. <案B>
3. 「なし」にする / やめる
```

## Step 1 — 置き場所を決める

`tracker-format.md` の置き場所と優先順で、リポジトリの `TRACKER.md` と個人の置き場所を確かめる。

- `--personal` があれば個人の置き場所に書く。ただし、リポジトリに `TRACKER.md` があると個人のものは読まれないので、
  そのことを伝えて、どちらを更新するか聞く。
- `--personal` が無く、リポジトリに `TRACKER.md` があればそれを更新する。個人のものだけがあれば、それを更新するか聞く。
- どちらにも無ければ、置き場所を聞く。チームで共有でき PR で直せる、リポジトリの `TRACKER.md` を勧める。
- 個人の置き場所のパスが `origin` から作れないときは、`tracker-format.md` のとおり聞く。

既にあれば読み、今あるトラッカーと決まりを控える（Step 5 の差分に使う）。

## Step 2 — 接続先を決める

引数（Jira の URL・サイトとキー、GitHub の `owner/repo`）、既存の運用ファイルの接続先、今のリポジトリの `origin` から、
どのツールのどの場所かを決める。決まらなければ聞く。複数のトラッカーを書くなら、それぞれについて Step 3〜4 を行う。
ツールの参照ファイルを読み、その「共通」で使えるかを確かめる。

## Step 3 — ツールから集める

参照ファイルの「運用を集める」で、読み取りだけで集める。

- **Jira**: 課題の種類（サブタスクの種類も）、ワークフローの状態と遷移、種類ごとの必須項目、直近の課題の使われ方
  （ラベル・コンポーネント・優先度・見積もりの項目・作業ログの有無・説明の見出し）
- **GitHub**: ラベル（状態らしいもの・種類らしいもの）、Issue テンプレート、直近の Issue の使われ方
  （ラベルの付け方・タイトルの付け方・本文の見出し）、使っていれば Projects の状態のフィールド

集めた結果から、`tracker-format.md` の各見出しに入る値を組み立てる。権限が無いなど取れなかったものは、取れなかったことを控える。

## Step 4 — 分からない決まりを聞く

読み取りからは分からない、運用の決まりを聞く。少なくとも次を確かめる（集めた結果から決まるものは聞かない）。

- 状態の流れの順番と、飛ばしてはいけない状態（GitHub では、どのラベルがどの状態を表すか）
- 頼むときの言い方とツールでの名前が違う状態
- 運用で必須にしている項目（ツールが必須にしていないもの）と、子に使う種類
- 工数を記録するか、どう記録するか
- ツールに無い操作の代わりの決まり（GitHub の工数、サブ issue・依存が使えないときなど）。決めなければ「なし」にし、
  そのときは `tracker:issue` が止まって聞くことを伝える

まとめて聞き、案があれば添える。

## Step 5 — 下書きを見せて確認する

`tracker-format.md` の形で下書きを作り、見せる。既にあれば、変わるところを差分で示す。

```markdown
# 運用ファイルの下書き

**書く場所**: <パス>（新しく作る | 更新する）
**接続先**: <ツール> / <場所>
**ツールから集めたもの**: <種類・状態・ラベル など> | **聞いて決めたもの**: <…> | **取れなかったもの**: <あれば>

<下書きの全文、または差分>

---
この内容で書きますか？（直してからでも構いません）
```

直してと言われたら直して再度見せる。

## Step 6 — 書いて報告する

確認した内容を書く（個人の置き場所なら、要るディレクトリも作る）。書いた後、次を伝える。

- 書いた場所と、書いたトラッカー
- 「なし」にした見出しと、後で決められること
- リポジトリの `TRACKER.md` なら、コミットして PR で共有すること
- 使い方の例: 「`/tracker:issue PROJ-12 をレビュー待ちにして`」
