# spec: 仕様を詰めて SPEC.md にする

作りたいものをユーザーと詰め、実装の基準になる `SPEC.md` を書く。
この仕様書は、`build` スキルが「方針からずれたか」「完了したか」を判断する唯一の基準になる。
曖昧なまま残すと、`build` が途中で止まって質問するか、ずれた実装になる。ここで詰め切ることが一番の目的である。

## 絶対に守ること

- **コードを変更しない。** 書くのは仕様書だけ。
- **コードを読めば分かることは聞かない。** 調べて分かったことは「こうなっているので、こうします」と案として示す。
- **質問は一度に3つまで、影響の大きい順に。** 各質問には、コードベースから考えたおすすめの答えを添える。
- **ユーザーが承認するまで `build` に進まない。**

## Step 1 — 入力を受け取る

| 入力 | 取得方法 |
|---|---|
| 文章（やりたいこと・メモ） | そのまま使う |
| ファイルパス | 読む |
| GitHub の Issue（`#123`、URL） | `gh issue view <番号> --json title,body,comments` |
| 空 | 会話の中で直前に話していた内容を使う。無ければ何を作りたいか聞く |

## Step 2 — コードベースを調べる

質問する前に、関係するコードを調べる。サブエージェントを起動できる環境では、調査を任せてメインの会話を軽く保つ。

調べること:

- 関係するファイル、似た既存機能、使われている設計の慣習
- 守るべきルール（`AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md` など）
- **チェックのコマンド** — テスト・ビルド・lint・型チェックの実行方法
  （`package.json` の scripts、`Makefile`、`justfile`、CI の設定、README など）。完了の条件に使う
- 仕様書の置き場所の慣習 — 既に `docs/specs/`、`docs/design/`、`specs/` などがあればそれに合わせる

## Step 3 — 詰める

次の観点で、決まっていないことを洗い出す。

| 観点 | 例 |
|---|---|
| 目的と範囲 | 何のために作るか。何を **やらない** か |
| 振る舞い | 正常系、異常系（入力エラー、通信失敗、権限なし）、境界（空、上限、重複） |
| データと API の形 | 入出力、保存するもの、公開する関数・エンドポイント・画面 |
| 方針 | 設計、新しく使うライブラリ、既存コードとの関係（拡張するか、置き換えるか） |
| 完了の条件 | どのチェックが通れば終わりか。自動で確かめられない部分の確認方法 |

決まっていないことのうち、**実装の結果が変わるもの** だけを質問する。
どちらでも結果がほぼ同じものは、聞かずに決めて仕様書の「決めた方針」に理由付きで書く。

質問の出し方:

```
決めたいことが3つあります（おすすめを先に書いています）。

1. 同じメールアドレスで2回登録されたとき — おすすめ: エラーにする
   （既存の users テーブルに一意制約があるため）
2. ...

聞かずにこう決めます（違えば言ってください）:
- 期限切れを返すメソッド名は overdue() にする
- 画面や CLI は作らず、関数として提供する（このリポジトリに画面や CLI が無いため）
```

聞かずに決めたことや置いた前提も、質問と一緒に短く示す。ユーザーが見落としに気づける最後の機会になる。

答えをもらったら、新たに分かったことを踏まえて、残りの決まっていないことを洗い出し直す。
**実装の結果が変わる未決事項が無くなるまで** 繰り返す。

## Step 4 — SPEC.md を書く

置き場所: リポジトリに仕様書の置き場所の慣習があればそれに従い、無ければ `docs/specs/<YYYY-MM-DD>-<slug>.md`。
`<slug>` は英小文字とハイフンで、作るものを表す短い名前にする。

テンプレート（見出しは変えない。`build` がこの見出しを読む）:

```markdown
# <作るもの>

- 状態: 下書き
- 作成日: <YYYY-MM-DD>
- 元: <Issue の URL など。無ければ省く>

## 目的

<なぜ作るか。1〜3行>

## やること

- <機能・変更を箇条書き>

## やらないこと

- <今回は範囲外にするもの。ここに書いたものに踏み込む必要が出たら、build は止まって質問する>

## 決めた方針

| 項目 | 決めたこと | 理由 |
|---|---|---|
| <設計・ライブラリ・API の形など> | <内容> | <ユーザーの回答 / コードの慣習 など> |

## 受け入れ条件

- AC-1: <確かめられる形で書く。「〜のとき〜になる」>
- AC-2: ...

## 完了の条件

- チェック: `<テストのコマンド>`、`<lint のコマンド>`、... がすべて成功する
- 受け入れ条件がすべて満たされている
- <自動で確かめられない確認があれば、その手順>

## 未決事項

- なし
```

受け入れ条件は、テストで確かめられる粒度で書く。`build` はこの番号（AC-1 など）で満たしたかどうかを判定する。

## Step 5 — 承認をもらう

仕様書のパスと要点（やること・やらないこと・決めた方針・受け入れ条件の数）を示し、承認を求める。

- 直したいと言われたら、直して再度見せる。
- 承認されたら、仕様書の `状態:` を `承認済み` に書き換える。

承認後に聞く:

```
仕様書を承認済みにしました: <パス>
このまま build で実装まで進めますか？
```

進める場合は `build` スキルを仕様書のパスを付けて呼ぶ（Claude Code と GitHub Copilot CLI: `/dev:build <パス>`、Codex: `$dev:build <パス>`）。
後で進める場合は、そのコマンドを伝えて終わる。
