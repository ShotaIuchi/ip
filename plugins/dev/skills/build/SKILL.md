# build: 仕様どおりに作り、レビューと修正を回して仕上げる

承認済みの仕様書を基準に、実装 → 確認 → 修正 を自動で回して仕上げる。
このスキルを実行している自分は **まとめ役** であり、実装と修正はサブエージェントに任せる。
まとめ役の会話を軽く保つことで、仕様を詰めた会話を引きずらずに実装でき、何周回しても文脈があふれない。

```
準備 → 実装（実装係） → [ チェック → 仕様との照合 → レビュー → 修正（修正係） ] × 最大3周 → 報告
```

## 絶対に守ること

- **仕様書が `状態: 承認済み` でなければ始めない。** 下書きなら `spec` で詰めて承認をもらうよう伝える。
- **作業用のブランチで作業する。** 作業中の変更を退避（stash）したり、捨てたり（reset、checkout）しない。
- **コミット・push しない。** 最後に `git-kit:commit` を案内する。
- **仕様からずれる必要がある時は、止めて質問する**（下の「止めて質問する時」）。それ以外は聞かずに決めて記録する。
- **テストを通すためにテストを曲げない**（削除・スキップ・期待値の書き換えで通さない。仕様が変わった場合を除く）。
- **周回の上限を守る。** 既定は3周。`--max-rounds <N>` で変えられる。

## 止めて質問する時

実装係・修正係・まとめ役の誰であっても、次に当たったら作業を止めて質問する:

1. 「やらないこと」に書いた範囲に踏み込む必要がある
2. 「決めた方針」を変える必要がある（別の設計、別のライブラリ、API の形の変更など）
3. 受け入れ条件・完了の条件を満たせない、または仕様の中で矛盾している
4. 公開している API、保存するデータの形、既存の振る舞いを、仕様に書かれていない形で変えることになる
5. 仕様に無い外部の依存（新しいライブラリ、外部サービス、権限）を足す必要がある

これ以外（内部の実装のやり方、関数の分け方、レビュー指摘の直し方など）は、聞かずに決めて「自分で決めたこと」に記録する。

質問の形（選択肢とおすすめを付ける）:

```
仕様からずれる判断が必要です（<1〜5 のどれか>）。
状況: <何が起きたか>
1. <案A>（おすすめ: <理由>）
2. <案B>
3. 中断する
```

ユーザーの答えは仕様書の「決めた方針」（範囲が変わるなら「やること」「やらないこと」も）に書き足してから再開する。
仕様書が常に最新の合意を表すようにするためである。

## サブエージェントの使い方

| 操作 | Claude Code | Codex | GitHub Copilot CLI |
|---|---|---|---|
| 起動する | Agent ツール（general-purpose） | `collaboration.spawn_agent` | `task` ツール（agent_type `general-purpose`） |
| 止まった係に答えを渡して再開させる | `SendMessage`（同じエージェントに送る） | `collaboration.followup_task`（`send_message` では再開しない） | 再開する方法が無ければ、答えとそれまでの経過を付けて新しく起動する |
| 終わるのを待つ | 完了通知を待つ | `collaboration.wait_agent` | 結果が返るのを待つ |

どの係にも、作業ディレクトリ（リポジトリのルートの絶対パス）を必ず渡す。サブエージェントやスキルは、まとめ役の作業ディレクトリを引き継がないことがある。

サブエージェントを起動できない環境では、自分で実装係・修正係の役を順に行う（文脈は増えるが、手順は同じ）。

## Step 1 — 仕様書を確認する

- 引数にパスがあればそれを使う。無ければ `docs/specs/` などから `状態: 承認済み` の仕様書を探し、
  1件ならそれを、複数ならどれにするか聞く。無ければ `spec` を案内して終わる。
- 仕様書を読み、`完了の条件` のチェックのコマンドと、受け入れ条件（AC-1 …）を控える。
- `未決事項` に「なし」以外が書かれていれば、始める前にユーザーに確認する。

## Step 2 — 準備する

リポジトリのルートに移動してから始める（以降のコマンド、サブエージェント、レビューはすべてここで行う）:

```bash
cd "$(git rev-parse --show-toplevel)"
git status --short
BASE=$(git rev-parse HEAD)
```

- 仕様書以外に未コミットの変更がある場合は、どうするか聞く（そのまま上に積む / 先にコミットしてもらう）。
  勝手に退避・破棄しない。
  ただし、テストやビルドが自動で作るファイル（`__pycache__/`、`node_modules/`、`dist/`、`.pytest_cache/` など、
  本来 `.gitignore` に入るもの）は変更とみなさない。これらは以降も差分・レビューの対象に含めない。
- 作業用のブランチを切る。未コミットの変更（仕様書を含む）はそのまま持ち越される:
  ```bash
  git switch -c dev/<slug>
  ```
  `<slug>` は仕様書のファイル名から先頭の日付と拡張子を除いたもの（`2026-11-24-slugify.md` なら `dev/slugify`）。
  既に同名のブランチがあれば、末尾に `-2` などを付ける。既に作業用のブランチ（`main` / `master` / 既定のブランチ以外）にいれば、切らずにそのまま使ってよい。
- `BASE` を最後まで控える。差分の確認とレビューの対象は常に `BASE` からの変更にする。

## Step 3 — 実装する（実装係）

実装係を新しい文脈で起動する。渡すのは仕様書のパスと次の指示だけにする（仕様を詰めた会話は渡さない）:

```
仕様書に従って実装してください。

仕様書: <パス>（最初に全文を読む）
作業ディレクトリ: <path>
守るルール: リポジトリの AGENTS.md / CLAUDE.md があれば読んで従う

進め方:
1. 関係するコードを読み、実装の計画を立てる（ユーザーへの確認は不要。そのまま進める）
2. 実装する。既存の慣習（命名、構成、エラー処理、テストの書き方）に合わせる
3. 受け入れ条件（AC-1 …）ごとに、確かめるテストを書く（テストの仕組みがあるリポジトリの場合）
4. 完了の条件のチェックを実行し、失敗したら実装を直す。テストを曲げない
5. コミットはしない。作業ツリーのファイルを、確かめるためだけに一時的に書き換えない（変異テストなどは、リポジトリの外のコピーで行う）

次に当たったら、その時点で作業を止め、status を "question" にして返す（推測で進めない）:
- 「やらないこと」の範囲に踏み込む必要がある
- 「決めた方針」を変える必要がある
- 受け入れ条件・完了の条件を満たせない、または仕様が矛盾している
- 公開 API・データの形・既存の振る舞いを、仕様に無い形で変えることになる
- 仕様に無い外部の依存を足す必要がある

次の JSON で返す:
{
  "status": "done | question",
  "question": { "reason": "上のどれか", "situation": "何が起きたか", "options": ["案A（おすすめ）", "案B"] },
  "changed_files": ["リポジトリのルートからの相対パス"],
  "decisions": ["自分で決めたこと — 理由"],
  "checks": [{ "command": "...", "result": "pass | fail", "note": "..." }]
}
```

- `status` が `question` なら、「止めて質問する時」の形でユーザーに聞き、仕様書に書き足してから、
  **同じ実装係** に答えを渡して再開させる。
- `done` なら、`decisions` を記録して Step 4 へ。

## Step 4 — 確認と修正を回す

1周は「確認（4-1〜4-3）→ 直すものを決める（4-4）→ 修正（4-5）」で、周回の上限は **修正の回数** の上限である。
上限の周の修正が終わったら、もう一度だけ確認（4-1〜4-3）を行って結果を確かめ、修正はせずに Step 5 へ進む。

周回 `n = 1` から始めて、次を繰り返す。

### 4-1. チェックを実行する

完了の条件のチェックのコマンドを、まとめ役が自分で実行する（実装係の報告をうのみにしない）。
失敗したものは、出力の要点（失敗したテスト名、エラー）を控える。

### 4-2. 仕様と照合する

新しい文脈のサブエージェント（照合係）に、仕様書のパスと `git diff $BASE` を渡して確認させる。
新しく作ったファイルも差分に出るよう、実装係・修正係が返した `changed_files` のうち未追跡のものだけを
`git add -N <ファイル>` で追跡対象にしておく（「追加する予定」の印だけを付け、中身はステージしない。`git status` では ` A` と表示される）。
仕様書と、自動で作られるファイルは対象にしない（仕様書は照合係が別に読む）。

```
仕様書と実装を照合してください。修正はしないでください。

仕様書: <パス>
差分: git diff <BASE>

確かめること:
1. 受け入れ条件ごとに、満たしているか（根拠のコード・テストの場所付き）
2. 「やること」に漏れが無いか
3. 「やらないこと」に踏み込んでいないか、仕様に無い変更（ついでのリファクタ等）が無いか
4. 「決めた方針」と違う実装になっていないか
5. 仕様そのものが曖昧・矛盾していて、どちらとも判定できない点が無いか（実装の誤りではなく、仕様の問題）

次の JSON で返す:
{
  "acceptance": [{ "id": "AC-1", "result": "met | partial | not_met", "evidence": "path:line", "note": "..." }],
  "missing": ["やることのうち未実装のもの"],
  "out_of_scope": ["path:line — 仕様に無い変更の内容"],
  "policy_mismatch": ["決めた方針と違う点（はっきり違うものだけ）"],
  "spec_questions": ["仕様が曖昧・矛盾していて判定できない点"]
}
```

### 4-3. レビューする

`review` スキル（Claude Code と GitHub Copilot CLI: `/review:review`、Codex: `$review:review`）を、対象 `since <BASE>` で呼ぶ
（`BASE` から作業ツリーまでの変更。仕様書は対象から外すよう伝える）。リポジトリのルートの絶対パスも一緒に伝える。
正確性は、そのスキルが実行環境の標準レビュー機能（`code-review` / `$review-agent` / Copilot の `code-review` サブエージェント）に任せる。
`review` スキルが無い場合は、標準レビュー機能だけを直接呼んで正確性を見る。

レビューの統合レポートはユーザーに個別に出さない。指摘は 4-4 の入力にし、最後に Step 5 の報告にまとめる。

### 4-4. 直すものを決める

| 出どころ | 直す対象 |
|---|---|
| チェック | 失敗したもの全部 |
| 仕様との照合 | `partial` / `not_met` の受け入れ条件、`missing`、`out_of_scope`（取り除く）、`policy_mismatch` |
| レビュー | Must と Should。Could は直さずに記録する |

次の指摘は直す対象にしない:

- 前の周で修正係が誤りと判断して直さなかった（`rejected`）指摘が、同じ場所・同じ内容でまた出たもの。
  「直さなかったもの」に、両方の言い分を付けて載せる。ただし、その食い違いが仕様の解釈によるものなら、下の「質問する」に回す

上から順に判定する:

1. **質問する** — 照合の `spec_questions` が空でない、または照合・レビューの指摘が「止めて質問する時」に当たる。
   上限に達していても、先に質問する（答えを仕様書に反映しないまま終えると、次に build したときに同じ問題が出るため）
2. **止めて聞く** — 直し方が行き来している。前の周で直した箇所について、同じ指摘がまた出た、
   または前の周と逆の方向に直すよう指摘された。止めて状況を報告し、どうするか聞く
3. **完了** — 直す対象が0件。Step 5 へ
4. **上限で停止** — 上限の周の修正が終わった後の確認である。残った問題を報告に載せて Step 5 へ
5. それ以外は 4-5 へ

### 4-5. 直す（修正係）

新しい文脈の修正係を起動し、仕様書のパスと直す対象の一覧を渡す:

```
次の問題を直してください。

仕様書: <パス>（最初に全文を読む。仕様が判断の基準）
差分の起点: <BASE>
直す対象:
  1. [チェック] <コマンド> が失敗 — <要点>
  2. [仕様] AC-2 を満たしていない — <内容>
  3. [Should] <タイトル> — <場所> — <詳細>
  ...

進め方:
1. 各問題について、直す前に原因を調べる（症状ではなく原因を直す。同じ問題が他の場所にもあれば一緒に直す）
2. 指摘が誤っている・仕様と食い違うと判断したら、直さずに理由を返す
3. 直したら、完了の条件のチェックを実行する。テストを曲げない
4. コミットはしない。作業ツリーのファイルを、確かめるためだけに一時的に書き換えない（変異テストなどは、リポジトリの外のコピーで行う）
（止めて質問する条件と、返す JSON は実装係と同じ。加えて "fixed": [番号], "rejected": [{"number": 番号, "reason": "..."}] を返す）
```

`question` が返ったら、実装係と同じく質問してから同じ修正係を再開させる。
まとめ役が 4-4 で質問した場合は、答えを仕様書に反映してから、その答えを直す対象に加えて修正係を起動する。
終わったら `n` を1つ増やして 4-1 に戻る。

## Step 5 — 報告する

```markdown
# build 結果

**仕様書**: <パス> | **ブランチ**: dev/<slug>（起点 <BASEの短いsha>） | **周回**: <n> / <上限>
**状態**: 完了 | 上限に達したため停止 | 直し方が行き来したため停止 | 質問待ちで停止

## 受け入れ条件
| ID | 結果 | 根拠 |
|---|---|---|
| AC-1 | 満たす | path:line、test_xxx |

結果は「満たす / 一部 / 満たさない / 要確認」のどれか。照合係とレビューで判定が分かれた場合は「要確認」にし、根拠に両方の判定を書く。

## チェック
- `<コマンド>`: 成功

## 直したもの
| 周 | 出どころ | 内容 |
|---|---|---|
| 1 | Should | <タイトル> |

## 直さなかったもの
| 内容 | 理由 |
|---|---|
| <Could の指摘> | Could のため記録のみ |
| <指摘> | 修正係が誤りと判断: <理由> |

## 既存の問題（参考）
- <変更前からある問題（code-review の pre_existing など）。今回は直さない>

## 自分で決めたこと
- <実装係・修正係の decisions>

## ユーザーに確認したこと
- <質問と答え。仕様書に反映済み。ユーザーに聞けず、まとめ役がおすすめを選んだ場合はその旨も書く>

## 変更
<git diff --stat $BASE>
```

最後に次の手を1行で示す: 「コミットするなら `git-kit:commit`、PR にしてからレビューを投稿するなら `review-pr`」。
