# triage-pr: PRのコメントを直して返信する

PR のレビューコメントを集め、対応が必要なものを直し、コミット・push し、各コメントに修正コミットを返信する。
返信しておくことで、レビュアー（や `review-pr` スキルの再レビュー）がどのコミットで直ったかを追え、
次回このスキルを実行した時に同じコメントを二重に処理しなくて済む。

## 絶対に守ること

- **push とコメントへの返信の前に、必ずユーザーの確認を取る。** どちらも外から見える操作である。
- force push、自動 rebase はしない。
- 質問・議論・承認のコメントには返信しない（直したコメントにだけ返信する）。
- 作業が終わったら（途中で止まった場合も）、必ず元のブランチに戻る。

## Step 1 — 対象のPRを決める

| モード | 起動条件 | 対象 |
|---|---|---|
| single | PR番号、`#N`、PR URL を指定 | そのPR1件（ドラフトでも処理する） |
| branch | 何も指定しない（デフォルト） | 今いるブランチに紐づくPR |
| repo | `--repo` | このリポジトリのオープンなPR全部 |
| repo + author | `--repo --author <login>`（複数可） | 指定した人が作ったオープンなPR |

自然な言い方も解釈する: 「自分のPRだけ」→ `gh api user --jq .login` で自分のloginを取得して `--author`、
「リポジトリ全体」→ `--repo`、「ドラフトも」→ `--include-drafts`。解釈したスコープは最初に1行で表示する
（例: `スコープ: repo, authors=[alice], ドラフト除外`）。解釈が本当に曖昧なときだけ確認する。

repo モードのPR一覧:

```bash
gh pr list --state open --json number,headRefName,baseRefName,url,isDraft,author,title --limit 100
```

`--include-drafts` が無ければドラフトを除外し、`--author` があれば作者で絞る。対象が0件なら、そう伝えて終わる。

**開始前のチェック:** 未コミットの変更がある場合は始めない。stash するかコミットするようユーザーに頼む
（PRブランチのチェックアウトで作業が失われるのを防ぐため、また後でコミットする変更をこのスキルの修正だけにするため）。

```bash
ORIGINAL_BRANCH=$(git branch --show-current)
```

PRが複数ある場合は **1件ずつ順番に** 処理する（並列にするとワーキングツリーが壊れる）。各PRについて
`gh pr checkout <number>` してから Step 2〜7 を行う。チェックアウトに失敗したら止めて報告する。

## Step 2 — コメントを全種類集める

PRのフィードバックは3か所に分かれている。全部集める。

**1. 行に付いたコメント（スレッド）** — 解決済みかどうかを知るため GraphQL で取る:

```bash
gh api graphql -f owner=<owner> -f repo=<repo> -F num=<number> -f query='
query($owner:String!,$repo:String!,$num:Int!){
  repository(owner:$owner,name:$repo){
    pullRequest(number:$num){
      reviewThreads(first:100){
        nodes{
          id isResolved isOutdated path line
          comments(first:50){ nodes{ databaseId author{login} body url createdAt } }
        }
      }
    }
  }
}'
```

**2. レビュー本文**（Approve / Request changes / Comment に添えた文章）:

```bash
gh api repos/<owner>/<repo>/pulls/<number>/reviews --paginate
```

**3. PRの会話コメント:**

```bash
gh api repos/<owner>/<repo>/issues/<number>/comments --paginate
```

スレッドは、返信まで含めて **スレッド全体を1単位** として扱う。最新のコメントが現在の要望を表していることが多い。

## Step 3 — 対応済みのものを飛ばす

次のものは評価の対象から外す:

- **解決済み（isResolved）のスレッド**
- **最後のコメントがこのスキルの返信のスレッド** — 本文に `<!-- triage-pr -->` を含むコメントが最後にある。
  その後にレビュアーが返信していれば（「まだ直っていない」等）、対象に戻す
- **このスキルが既に返信したレビュー本文・会話コメント** — その後の会話コメントに `<!-- triage-pr -->` と元コメントのURLを含むものがある

## Step 4 — 分類する

| 分類 | 意味 | 扱い |
|---|---|---|
| `actionable` | 具体的な変更要求（バグ修正、リネーム、テスト追加など） | Step 5 で直す |
| `question` | 説明を求める質問（「なぜXにした？」） | 飛ばして記録する |
| `discussion` | 具体的な変更要求のない設計の議論、「〜を検討しては」程度の提案 | 飛ばして記録する |
| `lgtm` | 承認、「いいですね」、絵文字のみ | 飛ばして記録する |
| `bot` | bot の投稿 | 飛ばして記録する |
| `already_done` | 今のコードで既に要望が満たされている（コードを読んで確認する） | 飛ばして記録する |
| `unclear` | 何を求められているか分からない | ユーザーに確認する |

「Yであるべき」のように具体的な変更を書いているものだけを `actionable` にする。

## Step 5 — 調べて直す

各 `actionable` について:

1. **参照されたコードを読む** — `path:line` と周辺。
2. **矛盾がないか確認する** — 同じ箇所に異なる提案があれば、新しい方・文脈がある方を基準にする。どちらとも言えなければユーザーに確認する。
3. **影響範囲を追う** — 波及する箇所があれば同じ修正で対処する。複数ファイル・設計に関わる場合は、
   サブエージェントを起動できる環境では調査を任せてメインの文脈を守る。
4. **直す** — コメントが求めた範囲に絞った最小限の変更にする。周辺のリファクタはしない。
5. **検証する** — ビルド・lint・テストのコマンドがあり短時間で終わるなら実行する。テストが壊れたら実装を直す（テストを曲げない）。

どのコメントのためにどのファイルを変えたかを記録しておく（Step 7 の返信で使う）。

直せない場合（コードが移動した、設計変更レベルの要求、テストが直らない）は、止めて状況を報告し、そのコメントを飛ばすか判断を仰ぐ。

1つのコメントのために多くのファイルを変えたくなったら立ち止まる。それは別のPRに値する問題かもしれない。

## Step 6 — コミットする

**`commit` スキル（git-kit）が使える場合はそれを呼ぶ。** 開始前のチェックで未コミットの変更が無いことを確認しているので、
この時点の変更は全てこのスキルの修正である。`commit` スキルの確認（未ステージを含めるか → 含める、分割案 → ユーザーが確認）に従う。

`commit` スキルが無い場合は、直近の `git log` の書き方に合わせて、コメント（またはまとまり）ごとにコミットする。
その場合もコミット前に分割案を見せて確認を取る。

コミット後、各コメントを直したコミットを特定する:

```bash
git log --format='%h %s' <開始時のHEAD>..HEAD -- <そのコメントで変えたファイル>
```

## Step 7 — push して返信する（確認を取ってから）

push と返信の内容をまとめて見せ、**1回確認を取る**:

```
PR #123 に次を行います:
- push: 3コミットを origin/<branch> へ
- 返信: 4件
  - <コメントURL> ← `a1b2c3d` で修正: nullチェックを追加
  - ...
よいですか？
```

OKなら:

**push**

```bash
git push
```

upstream が無くて失敗したら `git push -u origin <branch>`。リモートに新しいコミットがあって拒否されたら、
force push も自動 rebase もせず、状況を報告して判断を仰ぐ（返信もしない）。

**返信** — 各コメントの種類に応じて:

- 行のコメント（スレッド）: そのスレッドに返信する
  ```bash
  gh api repos/<owner>/<repo>/pulls/<number>/comments/<comment databaseId>/replies \
    -f body="\`<sha>\` で修正しました: <1行の説明>
  <!-- triage-pr -->"
  ```
- レビュー本文・会話コメント: PRに会話コメントを付ける（元コメントのURLを含める）
  ```bash
  gh pr comment <number> --body "<元コメントURL> への対応: \`<sha>\` で修正しました: <1行の説明>
  <!-- triage-pr -->"
  ```

スレッドを解決済みにはしない。解決するかどうかはレビュアー（または `review-pr` の再レビュー）が決める。

PRが複数ある場合は、ここまで終えてから次のPRへ進む。最後に `git checkout "$ORIGINAL_BRANCH"` で元のブランチに戻る。

## Step 8 — サマリー

```markdown
# PRコメント対応

**スコープ**: single | branch | repo (authors=<list>, drafts=<含む|除外>)

## PR #123 — <タイトル>

### 直した (N)
| コメント | 場所 | コミット |
|---|---|---|
| <URL> | path:line | a1b2c3d |

### 飛ばした (M)
| コメント | 分類 | 理由 |
|---|---|---|
| <URL> | question | 説明を求める質問 |
| <URL> | already_done | 既に要望どおり |

### 直せなかった (K)
| コメント | 理由 |
|---|---|
| <URL> | 設計変更が必要 |

### push / 返信
- 3コミットを origin/<branch> へ push、4件に返信
```

対応が必要なコメントが0件だった場合は、その旨を1行で伝えて終わる。
