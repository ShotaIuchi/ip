# loop: レビューと修正を、指摘が無くなるまで繰り返す

今の変更を `review` でレビューし、指摘とチェックの失敗を直す。これを、直すものが無くなるまで繰り返す。
このスキルを実行している自分は **まとめ役** で、直す作業はサブエージェント（修正係）に任せる。

```
準備 → [ チェック → レビュー → 直すものを決める → 直す（修正係） ] × 最大3周 → 報告
```

この文書は目的と決まりを書いたものである。チェックのコマンドや直し方は、そのリポジトリに合わせて自分で決める。

| 似たスキル | 違い |
|---|---|
| `review` | レビューしてレポートを出すだけ。直さない |
| `triage` | 指摘を調べ、ユーザーが選んだものだけを1回直す |
| `dev:build` | 承認済みの仕様書をもとに実装し、仕様との照合も含めて繰り返す |

## 絶対に守ること

- **コミット・push しない。** 最後に `git-kit:commit` を案内する。
- **作業中の変更を退避（stash）・破棄（reset、checkout）しない。** 未コミットの変更は、このスキルの対象そのものである。
- **テストを通すためにテストを曲げない**（削除・スキップ・期待値の書き換えで通さない）。
- **範囲と方針を勝手に変えない。** 下の「止めて聞く時」に当たったら止めて聞く。それ以外の直し方は、聞かずに決めて記録する。
- **周回の上限を守る。** 既定は3周。`--max-rounds <N>` で変えられる。

## 止めて聞く時

まとめ役・修正係のどちらでも、次に当たったら止めて聞く。

1. 直すために、公開している API、保存するデータの形、既存の振る舞いを変える必要がある
2. 新しい依存（ライブラリ、外部サービス、権限）を足す必要がある
3. 対象の変更の範囲を超えて、別の場所を広く直す必要がある、または設計を変える必要がある
4. 指摘どうし、または指摘とチェックが食い違い、どちらに合わせるかの判断が要る
5. 直し方が行き来している（前の周で直した箇所に同じ指摘がまた出た、または逆向きに直すよう指摘された）

```
判断が必要です（<1〜5 のどれか>）。
状況: <何が起きたか。指摘の番号・場所>
1. <案A>（おすすめ: <理由>）
2. <案B>
3. ここで止める（直したところまでで報告する）
```

答えをもらったら、それを直す対象に加えて続ける。ただし、上限の周の修正が終わった後の確認で聞いた場合は、答えを直さずに
「直さなかったもの」に「上限のため未対応（答え: …）」として載せ、Step 3 へ進む（上限を越えて直さない）。
「ここで止める」を選ばれたら、状態を「ユーザーの判断で停止」にして Step 3 へ進む。

## Step 1 — 準備する

- リポジトリのルートで作業する。マージ・リベースなどの途中なら、始めずに伝える。
- **対象と起点を決める。** 起点は、毎周のレビューで「どこからの変更を見るか」を表すコミットで、最後まで変えない。

  | 引数 | 起点 |
  |---|---|
  | 空 | 未コミットの変更があれば HEAD。無ければ、既定のブランチ（`origin/HEAD`、無ければ `main`、次に `master`）との分岐点 |
  | `since <ref>` | `<ref>` |
  | `branch BASE..HEAD` | `BASE` と HEAD の分岐点（HEAD は今いるブランチであること。違えば聞く） |
  | ファイルパス | HEAD。そのファイルの未コミットの変更だけを対象にする（変更が無いファイルは受け付けず、`review:review` を案内する） |
  | PR | 受け付けない（`triage-pr` を案内する） |

  対象の変更が無ければ、そう伝えて終わる。
- **`--with` を確かめる。** 名前が `claude` と `codex` 以外なら、始める前に一度だけ聞く。今動いている AI と同じ名前は外す。
  環境変数 `IP_PEER=1` のとき（別の AI として呼ばれているとき）は `--with` を無視する。確かめた一覧を控え、毎周それを渡す。
- **チェックのコマンドを探す**（テスト・ビルド・lint・型チェック。`package.json` の scripts、`Makefile`、`justfile`、CI の設定、README、`AGENTS.md` / `CLAUDE.md` など）。
  見つからなければ一度だけ聞く（無ければ、レビューだけで回し、報告に書く）。
  チェックには、ファイルを書き換えないもの（`--fix`・`--write`・formatter は使わない）、外に出ていかないもの（deploy・publish などではない）を選ぶ。
- 新しく作ったファイルもレビューの差分に入るよう、今回の変更に含まれる未追跡のファイルは `git add -N` しておく（中身はステージしない）。
  テストやビルドが自動で作るもの（`__pycache__/`、`node_modules/`、`dist/` など）、今回の変更との関係がはっきりしないもの、
  秘密らしいもの（`.env`、鍵など）は加えない。迷うものがあれば、一覧を見せて一度だけ聞く。`add -N` したファイルは報告に書く。

## Step 2 — 繰り返す

周回 `n = 1` から始める。上限は **修正の回数** の上限である。上限の周の修正が終わったら、もう一度だけ 2-1・2-2 で結果を確かめ、直さずに Step 3 へ進む。

### 2-1. チェックを実行する

まとめ役が自分で実行する（修正係の報告をうのみにしない）。失敗したものは、要点（テスト名、エラー）を控える。

### 2-2. レビューする

`review` スキル（Claude Code と Copilot CLI: `/review:review`、Codex: `$review:review`）を、対象 `since <起点>` で呼ぶ
（ファイルパスが対象なら、`since HEAD` で呼び、そのパス以外の指摘は採らない）。リポジトリのルートの絶対パスも伝える。
Step 1 で確かめた `--with` の一覧があれば、それを渡す。
`review` スキルが無い環境では、標準レビュー機能（`code-review` / `$review-agent` / Copilot の `code-review`）だけを直接呼ぶ。
レビューのレポートは周ごとにユーザーに出さず、2-3 の入力にする。

### 2-3. 直すものを決める

| 出どころ | 直す対象 |
|---|---|
| チェック | 失敗したもの全部 |
| レビュー | Must と Should。Could は直さずに記録する。`review` が「既存の問題」とした変更前からの問題は直さない |

前の周で修正係が誤りと判断して直さなかった指摘が、同じ場所・同じ内容でまた出たら、直さずに「直さなかったもの」に両方の言い分を載せる。

上から順に判定する。

1. **止めて聞く** — 「止めて聞く時」に当たる（上限に達していても先に聞く）
2. **完了** — 直す対象が0件。Step 3 へ
3. **上限で停止** — 上限の周の修正が終わった後の確認である。残った問題を報告に載せて Step 3 へ
4. それ以外は 2-4 へ

### 2-4. 直す（修正係）

新しい文脈の修正係を起動し、リポジトリのルートの絶対パス、起点、直す対象の一覧を渡す。修正係への指示:

```
次の問題を直してください。

作業ディレクトリ: <path>
変更の起点: <起点>（git diff <起点> が今回の変更）
直す対象:
  1. [チェック] <コマンド> が失敗 — <要点>
  2. [Must] <タイトル> — <場所> — <詳細>
  ...

進め方:
1. 各問題について、直す前に原因を調べる（症状ではなく原因を直す。同じ問題が他の場所にもあれば一緒に直す）
2. 指摘が誤っていると判断したら、直さずに理由を返す
3. 直したら、チェック <コマンド> を実行する。テストを曲げない
4. コミットはしない。退避・破棄（stash、reset、checkout）もしない
5. 公開 API・データの形・既存の振る舞いを変える、依存を足す、範囲を超えて広げる、設計を変える必要があれば、直さずに止めて理由を返す

次の形で返す:
{ "status": "done | question", "question": { "reason": "...", "options": ["案A（おすすめ）", "案B"] },
  "fixed": [番号], "rejected": [{ "number": 番号, "reason": "..." }],
  "changed_files": ["..."], "decisions": ["自分で決めたこと — 理由"] }
```

| 操作 | Claude Code | Codex | GitHub Copilot CLI |
|---|---|---|---|
| 起動する | Agent ツール（general-purpose） | `collaboration.spawn_agent` | `task` ツール（agent_type `general-purpose`） |
| 止まった係に答えを渡して再開させる | `SendMessage` | `collaboration.followup_task` | 答えとそれまでの経過を付けて新しく起動する |

サブエージェントを起動できない環境では、自分で修正係の役をする。

`question` が返ったら「止めて聞く時」の形で聞き、答えを渡して同じ修正係を再開させる。
終わったら、新しく作られたファイルを `git add -N` し、`n` を1つ増やして 2-1 に戻る。

## Step 3 — 報告する

```markdown
# loop 結果

**対象**: <対象>（起点 <短い sha>） | **周回**: <n> / <上限>
**状態**: 完了 | 上限に達したため停止 | 直し方が行き来したため停止 | ユーザーの判断で停止
**一緒に動かした AI**: <review の報告の値。`--with` が無ければ書かない>

## チェック
- `<コマンド>`: 成功 / 失敗（<要点>）

## 直したもの
| 周 | 出どころ | 内容 |
|---|---|---|
| 1 | [Must] [セキュリティ] | <タイトル> — `path:line` |

## 直さなかったもの
| 内容 | 理由 |
|---|---|
| <Could の指摘> | Could のため記録のみ |
| <指摘> | 修正係が誤りと判断: <理由> |
| <指摘> | 上限に達したため未対応 |

## 既存の問題（参考）
- <review が「既存の問題」とした指摘>

## 追跡の印を付けたファイル
- <`git add -N` したファイル。中身はステージしていない。無ければ書かない>

## 自分で決めたこと
- <修正係の decisions>

## 変更
<git diff --stat <起点>>
```

最後に1行で次の手を示す: 「コミットするなら `git-kit:commit`」。
