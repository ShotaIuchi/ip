# triage: 指摘を調べてから直す

レビュー指摘を受け取り、コードに触れる **前に** 各指摘を調査し、調査結果を見せてから、ユーザーが選んだものだけを直す。
調査を先にすることで、症状ではなく根本原因を直せ、同じ問題が他の場所にもあれば一緒に見つかる。

```
レビュー入力 → 指摘を一覧化 → 1件ずつ調査 → 調査結果を提示 → ユーザーが選択 → 修正 → 検証 → サマリー
```

## Step 1 — 指摘を一覧化する

| 入力 | 取得方法 |
|---|---|
| 空 | 会話の中で直前に出た `review` スキルのレポートを使う |
| 番号（`1,3` / `Mustだけ`） | 直前のレポートから該当する指摘だけを使う |
| ファイルパス | ファイルをレビューレポートとして読む |
| 貼り付けたテキスト / 他ツールの出力 | テキストから指摘を抽出する |

`review` のレポートは Must / Should / Could / Good の見出しで構造化されている。
他の形式はベストエフォートで抽出し、各指摘に「何が問題か」と「場所」が最低限そろうようにする。
曖昧で特定できない指摘は推測せず、ユーザーに確認する。

**Good（良い点）は除外する。** 直す対象ではない。

一覧を表示する:

```
N件の指摘があります:
  1. [Must] 文字列補間によるSQLインジェクション — auth.ts:42
  2. [Should] ユーザー一覧でN+1クエリ — api.ts:55
  3. [Could] 入力バリデーション不足 — handler.ts:12
```

## Step 2 — 1件ずつ調査する

このステップは省略しない。まだコードは変更しない。

**指摘1件につき調査役を1つ** 割り当てる。サブエージェントを起動できる環境では、指摘ごとに1つずつ並列に起動する
（指摘が多い場合は4件ずつに分けて順に進める）。起動できない環境では、自分で1件ずつ調査する。

調査役への指示:

```
レビュー指摘を調査します。修正はせず、調査だけを行ってください。

作業ディレクトリ: <path>
指摘:
  重要度: <Must | Should | Could>
  タイトル: <title>
  場所: <location>
  詳細: <detail>
  推奨: <recommendation>

調べること:
1. 根本原因 — 報告された場所とその周辺を読み、データの流れを追い、表面の症状ではなく原因を特定する
2. 影響範囲 — 呼び出し元・呼び出し先、同じパターンがコードベースの他の場所にもあるか
3. テスト状況 — 関連するテストはあるか、この問題をカバーしているか、修正で壊れそうなテストはあるか、追加すべきテストは何か
4. 指摘の妥当性 — 指摘が誤っている・既に対処済み・意図的な設計である可能性はないか
<セキュリティの指摘、または非推奨API・ライブラリの使い方に関する指摘で、Web検索が使える場合のみ>
5. 現在の推奨 — 公式ドキュメントやセキュリティアドバイザリーを検索し、推奨される直し方と注意点を出典URL付きで調べる

次の JSON で返す:
{
  "root_cause": "根本原因",
  "valid": "yes | no | partial — 理由",
  "affected_files": ["path:line", ...],
  "same_pattern_elsewhere": ["path:line — 説明", ...],
  "tests": {
    "existing": ["test_file:test_name — 何をカバーしているか"],
    "covers_issue": true,
    "needed": ["追加すべきテスト"],
    "at_risk": ["修正で壊れる可能性のあるテスト"]
  },
  "best_practice": "推奨される直し方（調べた場合のみ）",
  "sources": ["URL — 説明"],
  "fix_size": "small | medium | large — 理由",
  "confidence": "high | medium | low"
}
```

## Step 3 — 調査結果を提示して選んでもらう

```markdown
# 調査結果

## 1. [Must] 文字列補間によるSQLインジェクション — auth.ts:42
**原因**: `buildQuery()` がユーザー入力をSQL文字列に直接連結している。
**同じパターン**: `search.ts:78`、`report.ts:33` にもある。
**テスト**: `auth.test.ts:testLogin` は正常系のみ。不正入力のテストなし。
**推奨**: パラメータ化クエリ（出典: <URL>）
**修正規模**: 中（3ファイル） | **確信度**: 高

## 2. [Should] N+1クエリ — api.ts:55
...
```

指摘の妥当性が `no` のものは「直さない方がよい」と理由を添えて示す。
指摘より広い範囲に同じ問題が見つかった場合は、そのことを明示する。

最後にどれを直すかを聞く:

```
どれを直しますか？（例: "1,3"、"all"、"Mustだけ"）
```

## Step 4 — 選ばれた指摘を直す

各指摘について、調査結果に基づいて直す:

1. 症状ではなく **根本原因** を直す
2. 調査で見つかった影響ファイル・同じパターンも直す
3. 調査で「必要」とされたテストを追加・更新する
4. 推奨と注意点があればそれに従う

順序: ある指摘の修正が別の指摘のコードに影響するなら、影響する方を先に直す。依存が無ければ Must → Should → Could の順。

各修正後:
- プロジェクトにビルド・lint・テストのコマンドがあり、短時間で終わるなら実行する
- 修正でテストが壊れたら、テストを曲げずに実装を直す

修正が想定より大きくなる場合（設計変更が必要など）は、黙って大きく変えずに、状況を説明してユーザーに判断を仰ぐ。

## Step 5 — サマリー

```markdown
# 修正サマリー

## 直した指摘
| # | 指摘 | 変更ファイル数 | 追加テスト数 |
|---|---|---|---|
| 1 | SQLインジェクション — auth.ts:42 | 3 | 2 |

## 直さなかった指摘
| # | 指摘 | 理由 |
|---|---|---|
| 2 | N+1クエリ | 未選択 |

## 検証
- ビルド: 成功
- テスト: 24件成功、0件失敗（新規3件）

## 備考
- SQLインジェクション修正の際、search.ts と report.ts の同じパターンも直した（調査で発見）
```

コミットはしない。最後に1行で「コミットするなら `commit` スキル」と伝える。
