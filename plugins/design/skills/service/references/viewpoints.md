# 詰める観点

文書ごとに、決まっていないことを洗い出すときの観点。全部を聞くためのものではない。
**結果が変わるものだけ** を質問し、どちらでも結果がほぼ同じものは聞かずに決めて書く。

## 構想（concept.md）

| 観点 | 例 |
|---|---|
| 課題 | 誰が、どんな場面で、何に困っているか。今はどうしのいでいるか |
| 登場人物 | 使う人、お金を払う人、データを出す人、運営する人。それぞれに何を提供するか |
| 違い | 似たサービス・今のやり方と比べて、何が違うか |
| 収益 | 誰から何に対して受け取るか。無料なら費用の出どころ |
| リスク | 法令、データが集まらない、悪用、費用、競合 |
| 進め方 | 最初の Phase で何を確かめるか。続ける・やめる基準 |

## 用語集（glossary.md）

- 同じものを指す言葉が複数出ていないか（例: 「ユーザー」と「利用者」）。1つに決める
- 似ているが違うものの区別（例: 「商品」と「品目」、「店」と「組織」）
- 権限・役割の名前と、データの名前がぶつかっていないか

## 要求仕様（requirements.md）

| 観点 | 例 |
|---|---|
| 振る舞い | 正常系、異常系（入力エラー、通信失敗、権限なし）、境界（空、上限、重複） |
| データ | 何を持つか、誰のものか、いつ消すか、公開範囲 |
| アカウントと権限 | アカウントの種類、誰が何をできるか |
| 悪用 | なりすまし、スパム、虚偽のデータ、それを見つけて止める決まり |
| 法令・規約 | 個人情報、特定商取引法、ストアの規約、業界の規制 |
| 非機能 | 可用性、データ損失の許容、復旧時間、応答時間、規模 |
| 数値 | しきい値、期限、上限。初期値と、見直すときに見る指標 |

## 基本設計（design.md）

| 観点 | 例 |
|---|---|
| 構成 | 部品の分け方（1つにまとめるか、分けるか）と、その理由 |
| 技術 | 言語、フレームワーク、DB、クラウド。既存のコードや開発の原則との関係 |
| データモデル | テーブル・エンティティ、関係、どこに置くか（DB、オブジェクトストレージ、キャッシュ） |
| 機能の仕組み | 要求仕様の決まりを、どの部品がどう実現するか |
| 非同期と整合性 | キュー、再送、二重処理の防止、部分的な失敗 |
| セキュリティ | 認証・認可、秘密情報、入力の扱い、通信、監査 |
| 運用 | 監視、障害の検知と連絡、バックアップ、費用 |
| 品質 | テスト、静的解析、CI で何を自動で確かめるか |

技術や構成を、ほかの案と比べて選んだときは、判断記録にする。

## ロードマップ（roadmap.md）

- 各 Phase に、どの機能を、どこまで出すか
- 最初の Phase は、構想の「最初の Phase で検証すること」を確かめるのに必要な最小限か

## 開発の原則（.claude/rules/development-principles.md）

- 誰がコードを書くか（人 / AI）。AI が書くなら、作業量を判断の理由にしてよいか
- 選ぶときの基準の優先順位（安全、安定、正しさ、費用、作業量、運用の軽さ）
- 運用の作業（問い合わせ、確認、監視）を、どこまで自動化するか
