# service: サービス全体を設計して文書にする

作りたいサービスをユーザーと詰め、決まった構成の設計文書に書く。
文書は、人と AI エージェントの両方が読む前提で書く。AI が実装するときに迷わない粒度まで詰めることが目的である。

```
design:service（サービス全体） → dev:decompose（分解） → dev:spec（1機能の仕様） → dev:build（実装）
```

このスキルのフォルダには、次のものがある（パスはこのスキルのフォルダからの相対パス）:

| パス | 中身 | 使うとき |
|---|---|---|
| `references/conventions.md` | 書き方の決まりの **正本** と、その版 | Step 2、Step 4、Step 5 |
| `references/viewpoints.md` | 文書ごとに詰める観点 | Step 3 |
| `assets/` | 文書の雛形一式（`AGENTS.md`、`CLAUDE.md`、`docs/`、`.claude/rules/`）。置き場所はリポジトリでの置き場所と同じ | Step 4 |

## 絶対に守ること

- **コードを変更しない。** 書くのは設計文書だけ。コミットもしない。
- **既にある文書を、見せずに書き換えない。** 書き換える前に、変える内容を見せて確認を取る。新しく作るファイルは、まとめて確認を取ってから作る。
- **コードや既存の文書を読めば分かることは聞かない。** 調べて分かったことは「こうなっているので、こうします」と案として示す。
- **質問は一度に3つまで、影響の大きい順に。** 各質問には、おすすめの答えと理由を添える。
- **書き方の決まりは `references/conventions.md` に従う。** リポジトリの写しと食い違えば、正本を優先して更新を提案する（Step 2）。

## Step 1 — 入力と今の状態を確かめる

入力:

| 入力 | 取得方法 |
|---|---|
| 文章（作りたいもの・足したい部分・メモ） | そのまま使う |
| ファイルパス | 読む |
| GitHub の Issue（`#123`、URL） | `gh issue view <番号> --json title,body,comments` |
| 空 | 会話の中で直前に話していた内容を使う。無ければ何を作りたいか聞く |

リポジトリの状態を調べる（サブエージェントを起動できる環境では調査を任せてよい）:

- `docs/README.md` があるか。あれば、その中の目印 `<!-- design:conventions v<版> begin -->` があるか
- `AGENTS.md`、`CLAUDE.md`、`.claude/rules/` があるか、何が書かれているか
- 既にある設計文書・判断記録（`docs/` 以下の全体）
- コードがあれば、言語・フレームワーク・構成・インフラの定義・テストと CI のやり方

状態によって進め方を決める:

| 状態 | 進め方 |
|---|---|
| `docs/` が無い（新規） | Step 2 を飛ばし、Step 3 で全体を詰め、Step 4 で構成一式を作る。`AGENTS.md`・`CLAUDE.md`・`.claude/rules/` が既にあれば上書きせず、Step 4 で雛形の内容（文書へのリンクなど）を足す形にする |
| このプラグインの構成がある（目印がある） | Step 2 で決まりを照合し、Step 3 では入力に関係する部分だけを詰める |
| 別の構成の設計文書がある | 今の文書を読み、このプラグインの構成への合わせ方（どの文書をどこへ移すか、移さないか）を案として見せ、確認を取ってから進む。勝手に移したり消したりしない |

## Step 2 — 書き方の決まりを照合する（既存の場合）

`docs/README.md` の目印の間の文章と、`references/conventions.md` の「決まりの本文」を比べる。版の番号だけで判断せず、中身で比べる（行末の空白と空行の違いは無視する）。

- 同じなら、何も言わずに次へ進む。
- 違えば、差分を見せて更新を提案する:
  ```
  docs/README.md の書き方の決まりが、design プラグインの正本（版 <N>）と違います。
  <差分。足された決まり・変わった決まり・消えた決まりを箇条書きで>
  正本に合わせて更新しますか？（このリポジトリだけの決まりにしたいものは「このリポジトリだけの決まり」に移します）
  ```
  承認されたら、目印の間を正本の本文に置き換え、目印の版を正本の版にする。
  正本に無い決まりをリポジトリで残したいと言われたら、目印の外の「このリポジトリだけの決まり」に移す。
- 目印が無いが `docs/README.md` に書き方の決まりがある場合は、Step 1 の「別の構成」として扱う。

## Step 3 — 詰める

`references/viewpoints.md` の観点で、決まっていないことを洗い出す。
新規のときは、構想 → 用語 → 要求仕様 → 基本設計 → ロードマップ → 開発の原則 の順に詰める（前の文書の答えが後の文書の前提になるため）。
既存のときは、入力に関係する文書と、その変更が波及する文書だけを詰める。

決まっていないことのうち、**結果が変わるもの** だけを質問する。どちらでも結果がほぼ同じものは、聞かずに決める。

質問の出し方:

```
決めたいことが3つあります（おすすめを先に書いています）。

1. <問い> — おすすめ: <答え>
   （<理由。調べて分かったこと、比べた案>）
2. ...

聞かずにこう決めます（違えば言ってください）:
- <決めたこと>（<理由>）
```

聞かずに決めたことや置いた前提も、質問と一緒に短く示す。ユーザーが見落としに気づける最後の機会になる。
答えをもらったら、新たに分かったことを踏まえて洗い出し直し、**結果が変わる未決が無くなるか、ユーザーが「ここまでで書いて」と言うまで** 繰り返す。
決めきれないものは、未決として残す（Step 4 で判断記録の proposed か「その他の未決」に書く）。

### 判断記録にするもの

ほかの案と比べて選んだことのうち、後から変えると手戻りが大きいもの（技術の選定、構成の分け方、データの置き場所、外部サービスの選定など）は、判断記録にする。
質問の答えで決まったものも、聞かずに決めたものも対象である。
Step 3 では判断記録をまだ書かず、判断の題・比べた案・選んだ案（または未決）・理由を控えておく。
書くのは Step 4 で、ほかの文書と一緒に確認を取ってから書く（判断ごとに別に確認は取らない）。
書き方は `design:decision` スキルの Step 4 に従う（Claude Code・GitHub Copilot CLI: `/design:decision`、Codex: `$design:decision`）。
そのスキルが使えなければ、`docs/decisions/adr-template.md` の形で書き、`docs/decisions/README.md` の一覧に足す。
迷ったら、書き方の決まり（`references/conventions.md`）の「判断記録にするのは」に従う。

## Step 4 — 書く

### 新規のとき

`assets/` の雛形一式を、同じ相対パスでリポジトリに作る。作る前に、次の形で1回だけ確認を取る:

```
次のファイルを作ります（既にあるファイルは、足す内容だけを示します）。

新規:
- docs/README.md — 文書の一覧、書き方の決まり（版 <N>）
- docs/glossary.md — 用語 <N> 件
- ...
- docs/decisions/0001-xxx.md — <判断>（accepted）

既にあるファイルへの追記:
- AGENTS.md — <足す節と、その中身>

作りますか？（中身を先に見たい文書があれば言ってください）
```

- `<サービス名>` などの `< >` の部分を、詰めた内容で埋める。雛形の `< >` を残さない
- 埋める内容が無い節も、消さずに「未定」と書く（ほかの文書が節の番号で参照しているため。書き方の決まりの「節の番号」）。関係する未決があれば「未定（→ decisions/README.md）」とする
- 機能の節を増やすときは、末尾の番号で足す（要求仕様なら、雛形の最後の節の次から）
- 判断記録は、Step 3 で控えたものを番号順に作り、`docs/decisions/README.md` の一覧に足す。本文の該当する箇所には、決めたことと判断記録へのリンクを書く
- `docs/README.md` の目印の間には、`references/conventions.md` の「決まりの本文」をそのまま写し、`<版>` を正本の版にする
- `docs/specs/` は空のディレクトリにせず、`dev:spec` が最初の仕様書を作るまで作らない（`docs/README.md` の一覧には、リンクにせずに載せておく）
- 開発の原則（`.claude/rules/development-principles.md`）は、Step 3 で決めた内容で書く。決めていなければ作らず、
  `docs/README.md` の「開発の原則」の節と、`AGENTS.md` の「`.claude/rules/` の中のすべてのファイル」の項目を消し、
  `AGENTS.md` の冒頭の「`.claude/rules/` と `docs/` の文書へのリンクだけを置く」を「`docs/` の文書へのリンクだけを置く」にする
  （`.claude/rules/` に別のファイルがあれば、どちらも残す）
- `AGENTS.md` が既にある場合は、次のように足す:
  - 既にある見出しと中身は、そのまま残す
  - 雛形の「作業を始める前に必ず読む文書」と「文書を変更するとき」の節を、末尾に足す。雛形の題（`# <サービス名>`）と冒頭の説明文は足さない
    （冒頭の「中身の決まりはここには書かず」は、既にある決まりと矛盾するため）
  - 既にある中身に、設計文書と重なる決まり（用語の定義、設計の方針など）があれば、`docs/` や `.claude/rules/` に移すことを提案する。勝手に移さない
  - `CLAUDE.md` が既にあり `@AGENTS.md` を読み込んでいなければ、末尾に `@AGENTS.md` を足すことを提案する

### 既存のとき

変更する文書すべての変える内容（文書ごとに、足す節・直す行）と、作る判断記録を1回にまとめて見せ、確認を取ってから書き換える。
新しい節は、既にある節の番号を変えずに足す（末尾の番号か、関係する節の下位の節）。

### どちらでも守ること

- **用語集を先に書く。** 新しい言葉は、ほかの文書に書く前に glossary.md に足す
- **1つの決まりは1か所。** 同じ決まりを2つの文書に書かず、片方からリンクする（→ requirements.md §2.1 の形）
- **文書ごとに書くことを分ける。** 「なぜ」は構想、「何をするか」は要求仕様、「どう作るか」は基本設計、「いつ出すか」はロードマップ
- **判定に使う数値は、要求仕様の「判定に使う数値」にまとめる。** 本文には数値を書かず、そこへリンクする
- **図は Mermaid で書く。** 基本設計の §1（全体）と §2（部品）は必ず図にする
- `docs/README.md` の「最終更新」を今日の日付にする

## Step 5 — 整合を確かめる

書き終えたら、次を確かめて、見つけた食い違いは直す（直した内容は Step 6 で伝える）。
`docs/README.md` の目印の間（書き方の決まりの写し）は、例として `< >` や「→ §」を含むので、確かめる対象から外す:

- glossary.md に無い言葉で、意味のある言葉を使っていないか。同じものを別の言葉で呼んでいないか
- 「→ §」「→ <文書> §」のリンク先の節が実在するか
- 同じ決まりが2か所に書かれていないか
- ロードマップに機能の決まりが書かれていないか（名前と範囲だけか）
- `docs/decisions/README.md` の一覧が、`docs/decisions/` の判断記録のファイルと一致しているか（番号・題・状態）
- `docs/README.md` の「文書の一覧」が、実際の文書と一致しているか（まだ無い `specs/` はリンクにしていないか）
- 雛形の `< >` が残っていないか

## Step 6 — 結果を伝える

```markdown
# 設計の文書を<作りました | 更新しました>

| 文書 | 変更 | 要点 |
|---|---|---|
| docs/glossary.md | 新規 | 用語 N 件 |
| docs/decisions/0001-xxx.md | 新規 | <判断>（accepted） |

**決めたこと**: <主な判断を3〜5行>
**未決**: <判断記録の proposed と「その他の未決」の件数と、主なもの>
**整合の確認で直したこと**: <あれば>
```

最後に次の手を1行で示す: 「最初の Phase の機能を分けるなら `dev:decompose`、1つの機能を実装するなら `dev:spec`」。
