# merge: 論理的なぶつかりまで見てマージする

git は、同じ行を両側で変えたときしかコンフリクトを知らせない。片側が関数の引数を変え、もう片側がその関数の呼び出しを足すような
**論理的なぶつかり** は、マージは成功してもビルドやテストが壊れる。マイグレーションの番号や順番がぶつかることもある。
このスキルは、それらを探し、マージで生まれた問題を直してから、確認を取ってマージを確定する。

```
準備 → 両側の変更を見る → 論理的なぶつかりの候補を探す → 試しにマージ → チェック → 直す → 確認して確定
```

取り込む向きは `git merge <ブランチ>` と同じで、**今いるブランチ（ours）に、引数のブランチ（theirs）を取り込む**。
「main をブランチに取り込む」なら作業ブランチにいて `main` を、「ブランチを main に取り込む」なら `main` にいて作業ブランチを指定する。

この文書は手順の目的と決まりを書いたものである。調べ方・直し方の具体的なコマンドは、そのリポジトリの言語・ツールに合わせて自分で決める。

## 絶対に守ること

- **確認なしにマージを確定しない。** 早送りもマージコミットも、報告を示して OK をもらってから行う。
- **push しない。** 確定した後に、push するかを案内するだけにする。
- **rebase・pull・cherry-pick・octopus merge（3つ以上を一度に取り込む）は使わない。** ブランチを動かす操作（reset、`branch -f` など）や stash もしない。
- **プロジェクトのコマンドは、実行する前に毎回、コマンドを示して確認を取る。** チェック、依存のインストール、ロックファイルの作り直し、
  マイグレーションのツールなどが当たる。取り込む側のコード（`scripts`・`postinstall`・`Makefile` など）が手元で動くためである。
  git の読み取りだけのコマンド（`log`・`diff`・`show`・`grep` など）は確認しなくてよい。
  **git のフックも同じ扱いにする。** `core.hooksPath` がリポジトリの中（husky の `.husky` など）を指していると、
  `worktree add`・早送り・`commit` でそのフックが動き、取り込む側の版のフックが動くことがある。その場合は、これらの操作も確認の対象にし、
  フックが動くことを示す。
- **判断が要るものは直さずに止めて聞く**（下の「止めて聞く時」）。直し方が1つに決まるものだけを直す。
- **テストを曲げない**（削除・スキップ・期待値の書き換えで通さない）。片側の変更でテストの前提が変わったのに合わせる直しは、直し方が1つに決まるときだけ行う。
- `--no-verify` は使わない。コミットのフックが失敗したら原因を報告する。
- **中断は `git merge --abort`。** このスキルが始めたマージにだけ使う。`git clean` で未追跡のファイルをまとめて消さない。

## 止めて聞く時

次に当たったら、その時点で止め、状況と選択肢（おすすめを先頭に）を示して聞く。

- 始める前の状態が整っていない（Step 1）、どのブランチを取り込むか決まらない、手元とリモートの版がずれている（Step 2）
- プロジェクトのコマンドを実行する（確認を取る）
- 論理的なぶつかりや文字のコンフリクトの直し方に、どちらの意図に寄せるかの判断が要る
  （例: 新しい引数に渡す値、両側が同じものを別の形に変えた、仕様が食い違う、データの移行の順番が変わる、適用済みかもしれないマイグレーションを動かす）
- チェックが、マージで生まれた問題で失敗し、直し方が決まらない。または、同じ失敗を直しても通らない
- 確定する前（報告を示して確定してよいか聞く）

```
<何を決めるか>
状況: <何が起きたか。根拠のファイル・行・コミット>
1. <案A>（おすすめ: <理由>）
2. <案B>
3. 中断する（試しのマージを始めていれば git merge --abort でマージの前に戻す）
```

## Step 1 — 準備する

リポジトリのルートで作業する。次のどれかに当たれば、始めずに伝える（stash や reset で片付けない）。

- 未コミットの変更がある（未追跡のファイルを含む）。マージの結果と混ざるため
- マージ・リベース・cherry-pick・revert・bisect などの途中である
- detached HEAD である

## Step 2 — 取り込むブランチを決める

- 引数があれば、それを theirs にする。無ければ既定のブランチ（`origin/HEAD` が指すもの。無ければ `main`、次に `master`）を theirs にする。
  今いるのが既定のブランチそのもので引数が無ければ、何を取り込むか聞く。
- 既定のブランチがどちらの側かを控える（マイグレーションの付け直しで使う）。
- `git fetch` してリモートの最新を取る（対話の入力待ちで止まらないよう `GIT_TERMINAL_PROMPT=0` を付ける。失敗したら、手元のまま続けるか聞く）。
- theirs の手元のブランチがリモートより古ければ、「リモートの版を取り込む（おすすめ）/ 手元の版のまま」を聞く。
  ours がリモートより古い・ずれているときも伝えて、続けるか聞く。手元のブランチをリモートにそろえる操作（pull・reset）はしない。
- 調べる版と取り込む版がずれないよう、ours と theirs のコミット（sha）を控える。

**早送りできるとき**（ours が merge-base と同じで、theirs 側しか変わっていない）は、論理的なぶつかりは起きない。
そう伝え、確認してから、控えた theirs の sha を `git merge --ff-only` で取り込んで終わる。theirs が既に取り込まれているときは、そう伝えて終わる。

## Step 3 — 両側の変更を見る

merge-base を起点に、ours 側と theirs 側で何が変わったかを、それぞれのコミットログと差分で見る。
コミットメッセージから、両側の変更の意図もつかむ（文字のコンフリクトや、直し方の判断に使う）。

## Step 4 — 論理的なぶつかりの候補を探す

片側で変えた・消したものを、もう片側が使っていないか。両側が同じものを新しく足していないか。これを探す。
少なくとも次を見る（当てはまらないものは飛ばす）。

| 種類 | 例 |
|---|---|
| 関数・メソッド・クラス | 片側が引数・戻り値・名前を変えた、消した。もう片側が、その古い形の呼び出し・継承・実装を足した |
| 両側が同じものを足す | 同じ名前の関数・クラス、同じルート・エンドポイント、同じ設定キー・enum の値・エラーコード、同じ CLI オプション |
| 定数・設定・環境変数 | 片側がキー・名前・意味を変えた。もう片側が古いキーを使った |
| API の形 | 型・スキーマ・エンドポイント・イベントの形が片側で変わり、もう片側が古い形で使っている |
| マイグレーション | 両側が足して、番号・タイムスタンプが重なる、依存先（head・leaf）が分かれる。片側がスキーマを変え、もう片側がその前提でないコードやマイグレーションを足した |
| 依存とロックファイル | 両側が依存を変えた（ロックファイルを文字の上でマージした結果は正しくない）。片側が上げた版を、もう片側が前提にしている |
| テストの前提 | fixture・モック・テスト用のデータ・ヘルパーが片側で変わり、もう片側がそれを使うテストを足した |

探し方は自分で決める。例えば、片側の差分から変わった名前を取り出し、もう片側の差分（増えた行）とマージ後のコードを grep する。
LSP が使えれば参照の検索に使う。マイグレーションは、ツールの確認コマンド（`alembic heads`、`makemigrations --check` など）があれば使う
（プロジェクトのコマンドなので確認を取る）。見つけた候補は、ファイルを読んで本当にぶつかるかを確かめてから控える。

## Step 5 — 試しにマージする

```bash
git merge --no-commit --no-ff '<theirs の sha>'
```

確定はしない。マージを始めたことを控える（中断で `--abort` してよいのは、このマージだけである）。

- **文字のコンフリクト** は、両側の差分とコミットメッセージから意図を読んで解く。意図が食い違えば聞く。
- **Step 4 の候補を直す。** 直し方が1つに決まるものは直し、判断が要るものは聞く。直し方が1つに決まる例:
  - 片側の新しい引数・名前に、もう片側で増えた呼び出しを合わせる（渡す値が決まる場合だけ。決まらなければ聞く）
  - 両側が同じものを足し、中身も同じなら1つにまとめる
  - マイグレーションの番号・依存が重なったら、既定のブランチの側（適用された環境がありうる）は動かさず、もう片側を付け直す。
    付け直すマイグレーションを名前で参照しているもの（同じ側の後のマイグレーションなど）も合わせる。
    どちらも既定のブランチでない、適用済みの様子があるときは聞く
  - 両側が依存を変えたときは、マージした宣言からパッケージマネージャーでロックファイルを作り直し（確認を取る）、
    両側が上げた版が残っているかを確かめる。片側だけが変えたなら、その側のロックファイルが正しい
- 直したファイルは、直したらその場でステージする（`git merge --abort` は、ステージしていない変更があると失敗するため。ステージしておけば中断で一緒に捨てられる）。
- このスキルが新しく作ったファイル（付け直したマイグレーションなど）は、中断のときに消せるよう控える。

## Step 6 — チェックを回す

プロジェクトのチェック（ビルド・型チェック・テスト・lint・マイグレーションの確認）を、`package.json` の scripts、`Makefile`、`justfile`、
CI の設定、README、`AGENTS.md` / `CLAUDE.md` などから探す。見つからなければ一度だけ聞く（無ければ、候補の確認だけで進め、報告に書く）。
実行するコマンドを示して確認を取ってから、マージした結果で実行する。

- **失敗したら、両側と比べる。** 同じチェックを ours と theirs の版でも実行し（`git worktree add` でリポジトリの外に出して実行し、終わったら外す）、
  どちらかで既に失敗していたものは「元からの失敗」として分ける。マージした結果でだけ失敗するものが「マージで生まれた問題」である。
  両側で実行できない（依存の準備ができない など）ときは、どちらかの側の変更が関わる失敗を、マージで生まれた問題として扱う。
- **マージで生まれた問題を直す。** 直し方が1つに決まるものは直し、もう一度チェックを回す。判断が要るものは聞く。
  同じ失敗を直しても通らない、直し方が行き来するときは、止めて聞く。
- **チェックが通っても、Step 4 で控えた候補が残っていれば直す**（設定キーの名前など、テストで捕まらないぶつかりがあるため）。
- チェックが追跡しているファイルを書き換えたら（formatter、`lint --fix`、コードの生成など）、直した変更と分けて示し、含めるか戻すかを聞く。

## Step 7 — 確認して確定する

報告（Step 8 の形）を示し、確定してよいか聞く。

- **確定する** なら、このスキルが直したファイル・作ったファイルがステージされていることを確かめ、`git commit` でマージコミットを作る。
  それ以外に増えた未追跡のファイル（チェックが作ったものなど）はステージせず、一覧にしてどうするか聞く。
  1行目は `Merge branch '<theirs のブランチ名>' into <ours のブランチ名>` にする（sha で取り込んだので、git が用意する1行目は sha になっているため）。
  本文に、見つけた論理的なぶつかりと直した内容を書く。
  直した変更は、別のコミットにせず、このマージコミットに含める（どのコミットでもビルドとテストが通るようにするため）。
- **中断する** なら、次の順に戻す。
  1. 今のマージがこのスキルの始めたものであることを確かめ、`git merge --abort` でマージの前に戻す
     （ステージしていない変更があって失敗するときは、それがこのスキルやチェックが書き換えたものかを確かめ、そうなら `git restore` で戻してから、もう一度 abort する。
     そうでなければ、一覧にして聞く）
  2. 残った未追跡のファイルのうち、このスキルが作ったと控えたものだけを消す。それ以外は一覧にして、どうするか聞く

確定した後は、push するかを案内する（自分では push しない）。

## Step 8 — 報告する

```markdown
# merge 結果

**向き**: <theirs>（<sha>）→ <ours>（<sha>） | **起点**: <merge-base の sha> | **状態**: 確定した | 確認待ち | 中断した

## 文字のコンフリクト
- `<path>` — <どう解いたか>（無ければ「なし」）

## 論理的なぶつかり
| 候補 | 場所 | 結果 |
|---|---|---|
| <例: total() に引数 tax_rate が増えた（ours）のに、cart.py が古い形で呼ぶ（theirs）> | `app/cart.py:4` | 直した / 聞いた / 問題なし |

## チェック
- `<コマンド>`: 成功 / 失敗（マージで生まれた問題: … / 元からの失敗: …）
- 実行を断られたコマンド: <あれば>

## マージコミット
<確定したなら sha と1行目。確認待ちなら、書く予定のメッセージ>
```

最後に、確定したなら「push するなら `git push`」、確認待ちなら「確定しますか？」と1行で示す。
