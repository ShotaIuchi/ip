# Smart Commit: 意味ごとの分割コミット

変更を分析し、論理的に関連する変更をグループ化して、ユーザーの承認後に依存関係順に個別のコミットを作成する。

## 絶対に守ること

- **未ステージの変更を含めるかは、最初にユーザーに確認する（デフォルトは含める）。**
  「含めない」を選ばれた場合、未ステージの変更には触れない。ファイルの一部だけステージされている場合も、未ステージ部分をコミットに混ぜない。
  そのため `git add <file>` でステージし直すことはしない（ファイル全体が入ってしまう）。必ず Step 6 のパッチ方式を使う。
- **ユーザーの承認なしにコミットしない。** 分割案を提示し、OKをもらってから実行する。
- **途中で失敗したら、まだコミットしていない変更をステージ済みの状態に戻してから止まる。**
- `--no-verify` は使わない。pre-commitフックが失敗したら原因を報告する。
- `git add -p`、force push、`git commit --amend`（ユーザーの指示がない限り）は使わない。

## ワークフロー

### Step 1: 前提チェック

```bash
git rev-parse --verify HEAD
```

失敗する（まだコミットが1つもないリポジトリ）場合は、**コミットせずに止まり**、その旨をユーザーに伝える。

### Step 2: 対象の確認

```bash
git status --short
```

ステージ済みの変更と、未ステージの変更（未追跡ファイルを含む）の両方を確認する。

**機密ファイルのチェック（ステージ前に行う）:**

一覧に `.env`、`*.pem`、`*.key`、`credentials*`、`*secret*` などの認証情報らしいファイルが含まれていれば、
ステージやコミットを進めずにユーザーに警告し、どうするか確認する。

**未ステージの変更がある場合:**

ステージ済み・未ステージそれぞれのファイル一覧を表示し、
「未ステージの変更もコミットに含めるか」をユーザーに確認する。**デフォルトは「含める」。**

- **含める（デフォルト）**: `git add -A` で全変更をステージしてから続行する
- **含めない**: ステージ済みの変更だけを対象に続行する。未ステージの変更には一切触れない
  （ステージ済みの変更が1つもなければ、その旨を伝えて終了する）

**変更が何もない場合:** その旨を伝えて終了する。

### Step 3: コミットメッセージ規約の特定

以下の優先順で規約を決める。

1. リポジトリに `commit.schema.md` があればそれに従う
2. なければ、直近のコミットから規約を読み取る:
   ```bash
   git log -n 30 --no-merges --format=%s
   ```
   次の点を合わせる:
   - **言語**（日本語 / 英語）
   - **prefix**（`feat:` などの type の有無、`feat(scope):` 形式か）
   - **チケットIDの書き方**（`PROJ-123`、`#42` の有無と位置）
   - **subjectの文体**（命令形か、体言止めか など）
3. 履歴が少なく判断できない場合のデフォルト:
   - 形式: `<type>: <subject>`
   - type: feat / fix / docs / style / refactor / chore / test
   - 言語: 日本語、subjectは50文字以内・末尾に句点なし

body は任意。変更の理由や背景があれば書く（1行72文字以内）。

**署名（Co-Authored-By など）について:** このスキルでは固定の署名行を書かない。
実行環境（Claude Code など）から署名を付けるよう指示されている場合は、その指示に従う。

### Step 4: チケットIDの特定

**Step 3 で「履歴にチケットIDを書く習慣がある」と判断した場合のみ**行う。習慣がなければIDは付けず、ユーザーにも聞かない。

以下の順で取得し、見つかった時点で確定する。

1. **ブランチ名から**（`git branch --show-current`）
   - `feature/PROJ-123-add-login` → `PROJ-123`（`[A-Z][A-Z0-9]+-\d+` はそのまま）
   - `fix/42-null-check`、`issue-789-refactor` → `#42`、`#789`（数字のみなら `#` を付ける）
2. **PRが閉じるIssueから**
   ```bash
   gh pr view --json closingIssuesReferences --jq '.closingIssuesReferences[].number' 2>/dev/null
   ```
   1件なら `#<番号>` を使う。複数あればユーザーに選んでもらう。
3. **ユーザーに確認** — 入力してもらうか、IDなしで進めるかを選んでもらう。

### Step 5: 分割案の作成と承認

#### 意味単位への分類

`git diff --cached` で差分を読み、変更を「意味単位」に分類する。意味単位とは、一つの目的や意図でまとまる変更のこと。

- **機能単位**: 同じ機能の実装と、そのテスト・ドキュメントは同じコミットにまとめる
- **変更の種類**: バグ修正、新機能、リファクタリング、設定、依存関係の更新などは分ける
- **1ファイルに複数の目的が混在**: ファイル全体を、最も支配的なグループに含める（ファイルより細かくは分けない）
- **リネーム・移動**: 旧パスと新パスは必ず同じグループに入れる
- **迷ったら**: まとめる。過剰な分割より、1つのコミットメッセージで自然に説明できる粒度を優先する

#### 順序の決定

各コミットの時点でコードが壊れていない順にする。目安:

1. インフラ・設定（.gitignore、設定ファイル等）
2. 依存関係の追加・更新
3. リファクタリング
4. バグ修正
5. 新機能
6. ドキュメントのみの変更

これは目安。実際の依存関係（Aが無いとBが動かない等）を優先する。

#### ユーザーへの提示

次の形式で提示し、承認を待つ。

```
分割案（3コミット）
1. chore: .gitignoreにdistを追加
   - .gitignore
2. refactor: utils関数名をsnake_caseに統一
   - src/utils.py, src/api.py
3. fix: #42 handlerのnullチェックを追加
   - src/handler.py
```

ユーザーが修正を指示したら（まとめる、分ける、メッセージ変更など）、案を直して再提示する。

### Step 6: コミットの実行（パッチ方式）

ステージ済みの内容をパッチとして保存し、グループごとにインデックスへ適用してコミットする。
`git apply --cached` はインデックスだけを変更し、作業ツリーには触れないため、未ステージの変更は保持される。

1. **ステージ済みの内容を保存し、ステージを空にする**（最初に1回だけ）:
   ```bash
   PATCH="$(mktemp)"
   git diff --cached --binary --no-renames > "$PATCH"
   git reset -q
   ```
   `$PATCH` のパスは最後まで控えておく（失敗時の復旧に使う）。

2. **グループごとに適用してコミットする:**
   ```bash
   git apply --cached --include='<path1>' --include='<path2>' "$PATCH"
   git commit -F - <<'EOF'
   <subject>

   <body（必要な場合）>
   EOF
   ```
   リネームは旧パスと新パスの両方を `--include` に指定する。

3. **完了後:** `git status --short` で、元々未ステージだった変更だけが残っていることを確認し、`$PATCH` を削除する。

#### 失敗した場合（pre-commitフックの失敗、apply の失敗など）

それ以上コミットを進めず、まだコミットしていない変更をステージ済みの状態に戻す:

```bash
git reset -q
git apply --cached --include='<未コミットのpath1>' --include='<未コミットのpath2>' ... "$PATCH"
```

その上で、何コミット目で何が原因で止まったか、どのファイルがステージ済みで残っているかを報告する。
`$PATCH` は削除せず、パスを伝える。

### Step 7: 結果の報告

```bash
git log --oneline -<コミット数>
```

作成したコミットの一覧と、未ステージの変更が残っていればその旨を伝える。

## 例

### 例1: ブランチ `feature/PROJ-123-auth`、履歴が `feat: PROJ-123 ...` 形式

ステージ済み: `.gitignore`、`src/auth.py`、`tests/test_auth.py`

1. `chore: PROJ-123 .gitignoreを追加` → `.gitignore`
2. `feat: PROJ-123 ユーザー認証機能を追加` → `src/auth.py`、`tests/test_auth.py`

### 例2: 履歴が英語・チケットIDなし

ステージ済み: `src/utils.py`（リネーム）、`src/api.py`（追従）、`src/handler.py`（nullチェック）

1. `refactor: rename util functions to snake_case` → `src/utils.py`、`src/api.py`
2. `fix: add null check to handler` → `src/handler.py`

### 例3: `src/app.py` の一部だけがステージされていて、「未ステージは含めない」を選んだ

ステージ済みの差分（パッチ）だけがコミットされ、`src/app.py` の未ステージ部分は作業ツリーに残る。
